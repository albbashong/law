# 검색 방법 에이전트(search_plan) 설계

- 작성일: 2026-11-16
- 위치: `/home/ubuntu/permit/law` (브랜치 feat/law-agent)
- 관련: `docs/superpowers/specs/2026-10-19-law-agent-design.md` (law_review 본 설계)

## 1. 왜 만드는가

law_review 는 지금 답변 모델이 **검색 깊이를 스스로 정한다.** 큰 모델(gpt-oss-120b)도 조문 목록만 보고 원문을 열지 않는 일이 있고
(2026-11-12 W1: 핵심 조문 제21조를 되돌림을 받고도 끝내 열지 않음), 작은 모델(4B·8B)은 한두 번 찾고 멈춘다.

목표는 **모델 크기와 상관없이 같은 깊이로 찾게 하는 것**이다. 방법은 "이 질문은 이 순서로 이 조문들을 열어야 한다"는
**검색 계획**을 답변 전에 따로 계산해 주고, 답변 모델은 그대로 따라 열고, 런타임이 지켰는지 점검하는 것이다.

## 2. 목표 · 비목표 · 반목표

목표
- 모든 법령 질문(건축·인허가뿐 아니라 청탁금지법 같은 생활 법령까지)에 검색 계획을 만든다.
- 계획은 **법령 데이터의 인용·위임 연결에서 계산**한다.
- 작은 모델(qwen3:4b · qwen3:8b · gemma4:e4b)로 답할 때 계획이 있으면 근거 품질이 뚜렷이 오른다.

비목표
- 이 에이전트가 답을 쓰지 않는다. 조문 원문을 모아 넘기지도 않는다(계획만 준다).
- 과거 검색 기록에서 배우는 방식(사례 기반)은 이번 범위가 아니다.
- permit-workflow · permit-workflow-prompt 수정.

반목표 (기술적으로 돌아가도 실패로 보는 것)
- 계획 규칙을 코드에 적는 것: "건폐율이면 제55조", 질문 낱말 → 조문 표 같은 **하드코딩·키워드 규칙**. 법률 용어(위임 문구
  "대통령령으로 정한다" 등) 자체를 인식하는 것은 허용 — 이미 `engine/follow.py` 가 그렇게 한다.
- LLM 이 후보에 없는 조문 번호를 계획에 넣는 것(지어낸 조문).
- 계획 때문에 큰 모델의 답이 나빠지는 것(①보다 ③-120b 가 떨어짐).

## 3. 흐름 (정해진 것)

```
사용자 질문
  │
  ▼
law_review 런타임 ──(모든 질문마다 먼저)──▶ search_plan 에이전트
  │                                            1) 후보 뽑기   (코드: law_search)
  │                                            2) 시작 조문 고르기 (LLM: 후보 안에서만)
  │                                            3) 경로 계산   (코드: DB 연결을 따라감)
  │◀──────────── 검색 계획 ────────────────────┘
  ▼
답변 모델: 계획 순서대로 law-mcp 로 조문을 연다 → 답을 쓴다
  ▼
런타임 점검: 계획의 '꼭 열 조문'을 실제로 열었나? 빠졌으면 그 조문만 짚어 되돌림 (pointer 되돌림과 같은 틀)
```

- **모든 질문마다** 부른다(답변 모델이 부를지 고르지 않는다).
- **LLM 은 시작 조문 고르기에만** 쓴다. 고르는 대상은 1)이 준 후보 목록으로 닫혀 있고, 고른 결과가 후보 안에 있는지 코드가 대조한다.
  후보 밖 값은 버린다.
- 시작 조문 고르기에 쓰는 LLM 도 시험 때는 **답변 모델과 같은 작은 모델**이다("작은 모델만으로 된다"를 보이기 위해).
- 답변 모델은 계획을 **따라 연다**. 계획의 조문 원문은 계획에 실리지 않는다.
- **주소가 있는 질문은 search_plan 이 직접 지역을 알아낸다.** 질문에 필지 주소가 있으면 law-mcp `parcel_zoning`(브이월드)을 먼저 불러
  시군구·용도지역을 정하고, 조례까지 한 번에 경로를 계산한다. 주소가 있는지는 키워드가 아니라 시작 조문을 고르는 **같은 LLM 호출**이
  함께 뽑는다(호출 수를 늘리지 않음). 브이월드 실패 시 '지역 필요'를 계획에 적고 나머지는 그대로 계산한다.
- **건축 질문의 `building_basis` 는 그대로 함께 쓴다.** 계획이 그 흐름을 대신하지 않는다. 계획은 building_basis 를 부를 단계로 두고,
  그 결과가 가리키는 조문(핵심 조문·위임 조문) 중 꼭 열 조문을 정한다. 지금 건축 문항 성능이 떨어지면 안 된다.

## 4. 데이터 (2026-11-16 실측, `data/lawdb.sqlite`)

| 표 · 종류 | 건수 | 쓰임 |
|---|---|---|
| `link` 인용 | 4,497,355 (그중 같은 조문 자기 자신 2,464,274 — 버림) | 조문→조문, 항·호까지(`제84조/1 → 제77조/1`, evidence "법 제77조제1항") |
| `link` 조례연계 | 392,419 (5.5만은 from_path 없음) | 조례 조문 → 상위 법 조문(법제처 lnkLsOrdJo) |
| `link` 체계 | 15,231 | 법률·시행령·시행규칙 묶음 |
| 별표로 가는 인용 | 185,029 | 조문 → 같은 법령 별표 |
| `doc` | 법령 5,628 · 자치법규 161,790 | |
| `unit` | 9,678,102 | 조·항·호 원문 |

**위임**은 따로 종류가 없고, 하위 법령이 상위 법령을 인용하는 **반대 방향 인용**으로 남아 있다
(국토계획법 제77조 ← 시행령 제84조 각 항, ← 조례 936건). 상위 조문의 위임 문구("대통령령으로 정하는", "조례로 정한다")는
`engine/follow.py` 의 `ORDIN_DELEGATION`·`DELEGATION_HINT`(법률 용어)로 이미 인식한다.

이미 있는 것: `engine/follow.py` — 조문 하나에서 위(up)·아래(down)로 깊이 제한 BFS. 조례는 지역이 있을 때만 그 지자체 것.
지금은 `law_article`(chain/depth 인자)·`building_basis` 가 깊이 1~2로 내부에서만 쓴다.

비어 있는 곳: **질문 → 시작 조문**은 연결 구조로 풀 수 없다. 검색 + LLM 고르기가 맡는다. 지금 오답이 나는 곳이 여기다
(G11: 조례 제56조 대신 제59조).

## 5. 검색 계획 — 넘기는 내용

계획은 순서 있는 단계 목록이다. 한 단계 = 열어 볼 조문 하나.

| 칸 | 뜻 |
|---|---|
| 법령명 · 조문 | `law_article` 에 그대로 넣을 수 있는 값(정식 명칭, "제77조" 꼴) |
| 관계 | 시작 / 상위 / 하위(위임 받음) / 조례 / 별표 / 인용 — 왜 이 조문을 여는지 |
| 꼭 열기 | 참이면 런타임이 열었는지 점검한다 |
| 이어진 조문 | 이 단계가 어느 단계에서 나왔는지 |

그 밖에: 계획을 만들다 멈춘 이유(지역이 없어 조례로 못 내려감 등 — follow 의 `more`) 를 함께 싣는다.
지역이 필요한데 질문에 없으면 그 사실을 계획에 적는다(되묻기는 law_review 의 기존 흐름이 한다).

**'꼭 열기'를 정하는 원칙** (데이터에서 계산): 시작 조문, 시작 조문이 위임하는 하위 조문(위임 문구가 있는 경우),
시작 조문이 기준을 넘기는 상위 조문(예: 건축법 제55조 → 국토계획법 제77조). 단순 인용(정의 조문 인용 등)은 꼭 열기가 아니다.
정확한 판정식은 설계자 몫(§9)이되 표·낱말 목록이 아니라 `link` 의 종류·방향·evidence 와 위임 문구 인식에서 나와야 한다.

## 6. 런타임 점검

- 답을 내기 전에 '꼭 열 조문'마다 그 조문 원문을 실제로 연 도구 결과가 있는지 대조한다.
- 빠진 조문이 있으면 그 조문만 이름 붙여 되돌린다(문장은 `.env` 설정값). 되돌림은 지금 pointer 되돌림과 같은 횟수 상한을 따른다.
- 상한을 넘겨도 못 열면 지금처럼 "확인되지 않았습니다" 꼬리표를 붙여 내보낸다.

## 7. 성공 기준

같은 평가 질문 세트를 세 조건으로 돌려 비교한다. 세트: `eval/golden.yaml` + 2026-11 무작위 100문항
(작업 폴더의 `rand100.yaml` — 골든셋·messy100 등에서 뽑은 것, 구현 때 `eval/rand100.yaml` 로 옮겨 커밋).

**[내 판단] 지표 정의**
- **근거 통과율** = 런타임 답 점검(조회 안 한 인용·법령명·수치·따옴표)이 꼬리표 없이 통과한 문항 비율. 지금 결과 JSON 에 남는 점검 결과로 잰다.
- **정답 조문 재현율** = `must_refs` 가 있는 문항에서 그 조문을 실제로 연 비율(기존 recall). 계획이 스스로 낸 '꼭 열기' 목록이
  아니라 **문항에 미리 적힌 정답**으로 재므로, 계획이 틀리면 점수도 떨어진다.
- **계획 준수율** = 계획의 꼭 열 조문 중 실제로 연 비율(보조 지표 — 계획을 따랐는지만 본다).

| 조건 | 답변 모델 | 검색 계획 |
|---|---|---|
| ① 기준 | gpt-oss-120b (공유 vLLM) | 없음 |
| ② | qwen3:4b · qwen3:8b · gemma4:e4b | 없음 |
| ③ | 같은 작은 모델들 (+ 120b) | 있음 |

- ③이 ②보다 **근거 통과율**과 **꼭 열 조문을 실제로 연 비율**이 뚜렷이 높고, ①에 가까워지면 성공.
- 조회하지 않은 조문 인용(환각)은 ③에서 ②보다 늘면 안 된다.
- ③-120b 가 ①보다 나빠지면 안 된다(반목표).

## 8. 제약

- 하드코딩·키워드 규칙 금지(법률 용어만 예외). 설정값은 `.env`, 키·LLM 주소는 커밋 금지(`.env.example` 에서 비움).
- permit-workflow · permit-workflow-prompt 수정 금지. HWP/PDF 저장 금지.
- 작은 모델은 이 PC 의 ollama(`OLLAMA_HOST` 가 정한 포트, 지금 :9001, OpenAI 호환 `/v1`)에서 돌린다.
  RTX 5080 16GB. 세 모델 모두 도구 호출 확인됨(2026-11-16). qwen 은 조문을 "55조"처럼 '제' 없이 적는다 — law-mcp 가 받는지 확인 필요.
- 기존 시험(런타임 442 · MCP 222) 은 계속 통과해야 한다.

## 9. 설계자에게 맡기는 것 (내 판단으로 정한 기본값 포함)

- **[내 판단] 배치:** search_plan 은 law_review 와 따로 띄우는 서버로 둔다(같은 공용 runtime 을 쓰는 새 에이전트 디렉터리,
  예 `agent/search_plan/`, 새 포트). 경로 계산(3단계)은 DB 와 `follow.py` 가 있는 **law-mcp 안의 새 도구**로 두고,
  search_plan 은 그 도구와 `law_search` 를 부르고 LLM 고르기만 한다.
- **[내 판단] LLM 엔드포인트:** search_plan 의 LLM 은 law_review 와 따로 설정한다(`.env`). 시험 때는 둘 다 같은 작은 모델.
- **[내 판단] 연결 방식:** search_plan 은 모델 루프가 필요 없는 정해진 순서(코드→LLM 한 번→코드)라 공용 runtime 의 루프를 쓰지 않는
  작은 A2A 서버로 만든다. law_review 쪽은 공용 runtime(`agent/runtime`, 이 리포에서 계속 고쳐 온 우리 사본)에 **'답 전에 부를 에이전트'
  설정(.env, 비우면 지금과 똑같이 동작)** 과 A2A 호출을 더한다. 설정이 비면 기존 시험·conformance 가 그대로 통과해야 한다.
- **[내 판단] '열었음' 판정:** 지금 인용 점검(`ungrounded`)이 쓰는 기준과 같게 한다 — 도구 결과 본문(pointer 로 표시된 목록 칸 제외)에
  그 조문이 나오면 연 것이다. 따라서 `law_article` chain 의 refs 발췌로 함께 온 조문도 연 것으로 친다(라운드 수를 아끼기 위해).
- **[내 판단] 시작 조문 개수와 실패:** 시작 조문은 여러 개를 고를 수 있다(상한은 설정값). LLM 이 고른 값이 모두 후보 밖이거나
  "후보에 맞는 조문이 없다"고 하면 **빈 계획**을 넘기고 law_review 는 지금처럼 스스로 찾는다(계획 때문에 나빠지지 않게).
  search_plan 이 실패·시간 초과해도 같은 처리.
- 후보 개수, 경로 깊이, 단계 상한, 꼭 열기 판정식의 세부.
- 계획을 답변 모델에게 보이는 방식(첫 사용자 메시지 뒤에 붙이기, 시스템 문장 등).
- 평가 도구(`eval/run_eval.py`)에 '꼭 열 조문을 연 비율' 지표 추가 방법.
