# A2A v1.0 호환 에이전트 구현 안내

**버전 2.1** · 2026-09-02

**표준 스펙이 아닙니다.** A2A Protocol v1.0 을 옮겨 적고, 그 위에 이 플랫폼의 프로파일과 구현 안내를 얹은 문서입니다. 표준의 지위를 가진 것은 **A2A 하나**이고 정본 사본이 `reference/` 에 있습니다 — 커밋 `c0f30b35390c` 로 고정했습니다. 이 문서와 어긋나면 **정본이 맞습니다.**

**구현 기술은 자유입니다.** 언어·웹 프레임워크·내부 구조·도구 호출 방식·모델 — A2A 는 아무것도 정하지 않습니다. 묶이는 것은 **밖으로 드러나는 경계**뿐입니다(2장·3장).

## 1. 개요

### 1.1 A2A 가 말하는 에이전트

**A2A 는 안을 들여다보지 않습니다.** 규격이 정하는 것은 한 가지뿐입니다.

> **A2A 계약을 말하는 HTTP 종단점.**

안이 LLM 이든 규칙 엔진이든 사람이 답하는 창구든 상관없습니다. 모델도, 도구도, 도구 호출 능력도 **A2A 의 요건이 아닙니다.** 규격은 에이전트를 *불투명한 것*으로 다루고, MCP 같은 것도 "쓸 수 있다"고 할 뿐입니다.

#### 이 플랫폼에서 말하는 에이전트

우리가 만드는 것은 그중 한 모양입니다 — **이건 우리 전제이지 A2A 의 정의가 아닙니다.**

**자연어 발화 하나를 받아, 자기 모델과 자기 도구로 자기 도메인 안에서 끝까지 처리해 결과를 돌려주는 독립 HTTP 서비스.**

- **발화를 받습니다.** 파싱된 인자가 아닙니다. 부르는 쪽이 "상품명을 뽑아서 넘겨야지" 하고 고민하지 않아도 되게 하는 것이 존재 이유입니다.
- **자기 모델을 가집니다.** 부르는 쪽의 모델을 빌려 쓰지 않습니다.
- **독립 서비스입니다.** 자기 프로세스, 자기 포트, 자기 수명.

이 모양을 따르지 않아도 **A2A 적합합니다.** 2장만 지키면 됩니다.

### 1.2 왜 A2A 인가 — 이 문서가 다루는 층

에이전트는 **불투명**합니다 — 부르는 쪽은 안에 무엇이 있는지 몰라야 합니다. MCP 를 쓰는지, SQL 을 치는지, 사람이 답하는지 알 필요가 없습니다. A2A 는 그 불투명한 것들을 동료로서 잇는 규격입니다.

이 플랫폼은 A2A 를 **그대로** 씁니다. 다만 A2A 가 비워 둔 자리가 있어(4.1절·4.2절) 그 부분을 이 문서가 채웁니다. 채운 부분도 A2A 의 확장 기구 안에서 채우므로, **A2A 만 아는 클라이언트도 우리 에이전트를 쓸 수 있습니다.**

```
 ┌─────────────────┐
 │  오케스트레이터   │
 └────────┬────────┘
          │  A2A / HTTP         ◀── 이 문서가 정하는 것
 ┌────────▼────────┐
 │     에이전트     │            ◀── 당신이 만드는 것
 └────────┬────────┘
          │  도구 호출 (MCP 등)  ◀── 별도 문서. 이 문서는 다루지 않는다
 ┌────────▼────────┐
 │       도구       │            ◀── 이미 있다고 가정한다 (1.5절)
 └─────────────────┘
```

**이 문서는 에이전트의 바깥 면만 정합니다.** 안에서 도구를 어떻게 부르는지 — MCP 든, 직접 HTTP 든, 데이터베이스 조회든 — 이 문서의 관심이 아니다. 밖으로 A2A 를 지키면 적합합니다.

도구를 MCP 서버로 만드는 일은 범위 밖이고 **별도 문서가 다룹니다.** 에이전트를 만들기 전에 도구가 이미 노출돼 있어야 합니다.

### 1.3 A2A 의 네 가지 개념

뒤에 나오는 요건은 전부 이 넷 위에 얹힙니다. **먼저 이것부터 익히면 나머지가 쉽습니다.**

```
  Context  ─ 대화 하나                    contextId
     │
     ├─ Task ─ 그 대화에서 시킨 일 하나    taskId
     │     ├─ Message  주고받은 발화       (역할 + Part 목록)
     │     └─ Artifact 그 일이 낸 결과물   (이름 + Part 목록)
     │
     └─ Task ─ 같은 대화의 다른 일
```

**Task — 시킨 일 하나.** 서버가 `taskId` 를 붙여 만들고, 정해진 상태(접수 → 처리 중 → 완료)를 따라 움직입니다. 오래 걸리는 일을 다루기 위한 그릇입니다 — 한 번 부르고 결과는 나중에 거둡니다.

**Context — 대화 하나.** 여러 Task 를 묶습니다. `"아까 그거 주문해줘"` 가 성립하려면 이전 Task 를 찾을 수 있어야 하고, 그 묶음이 Context 다.

**Message — 주고받은 발화 하나.** 누가 말했는지(`role`)와 무엇을 말했는지(`parts`)를 갖습니다. 사용자의 요청도, 에이전트의 되묻기도 Message 다.

**Artifact — 일이 낸 결과물.** 이름과 내용을 갖습니다. 답변 문장 하나일 수도 있고, 화면에 그릴 데이터일 수도 있습니다.

**Part — 내용 조각.** Message 와 Artifact 는 둘 다 Part 목록을 담습니다. Part 는 글(`text`)이거나 구조화된 데이터(`data`)거나 파일(`raw`·`url`)입니다.

#### 왜 Task 라는 그릇이 필요한가

에이전트는 모델을 부르고 도구를 부릅니다 — 수 초에서 수십 초가 걸립니다. 그동안 HTTP 연결을 붙들고 있으면 끊기고, 진행 상황도 알 수 없습니다.

그래서 A2A 는 **일을 만들고 나중에 거두는** 방식을 씁니다.

```
  ① POST /message:send   →  taskId 를 받는다 (즉시)
  ② GET  /tasks/{id}      →  끝났나? 아직이면 다시 (폴링)
  ③ GET  /tasks/{id}      →  끝났다. 결과를 읽는다
```

기다리는 편이 나으면 ①에서 끝날 때까지 막을 수도 있습니다. 둘 다 규격이 요구합니다(2.1절).

### 1.4 한 번 끝까지 따라가기

세부는 몰라도 됩니다. **모양만 눈에 익히면** 뒤가 편합니다.

```http
POST /message:send HTTP/1.1
Host: agent.example.com
Content-Type: application/a2a+json

{"message": {"messageId": "9f2b1c40-...", "role": "ROLE_USER",
             "parts": [{"text": "A-1023 두 개 주문해줘"}]},
 "configuration": {"returnImmediately": true,
                   "acceptedOutputModes": ["text/plain", "application/json"]}}
```
```http
HTTP/1.1 200 OK
Content-Type: application/a2a+json

{"task": {"id": "t_7c1e", "contextId": "c_3a90",
          "status": {"state": "TASK_STATE_SUBMITTED",
                     "timestamp": "2026-09-01T12:00:00.000Z"}}}
```
```http
GET /tasks/t_7c1e HTTP/1.1
```
```json
{"id": "t_7c1e", "contextId": "c_3a90",
 "status": {"state": "TASK_STATE_COMPLETED",
            "message": {"messageId": "b1d0...", "role": "ROLE_AGENT",
                        "taskId": "t_7c1e", "contextId": "c_3a90",
                        "parts": [{"text": "파란 머그컵 350ml 2개를 주문했습니다. 주문번호 O-88214."}]},
            "timestamp": "2026-09-01T12:00:06.220Z"},
 "artifacts": [
   {"artifactId": "t_7c1e:answer", "name": "answer",
    "parts": [{"text": "파란 머그컵 350ml 2개를 주문했습니다. 주문번호 O-88214."}]},
   {"artifactId": "t_7c1e:actions", "name": "actions",
    "parts": [{"mediaType": "application/json",
               "data": [{"type": "catalog.highlight", "sku": "A-1023"}]}]}],
 "metadata": {
   "https://<도메인>/ext/usage/v1": {"tokensIn": 3180, "tokensOut": 96},
   "https://<도메인>/ext/progress/v1": {"fraction": 1.0, "message": ""}}}
```

읽는 법 — ①에서 `taskId` 를 받고, ②에서 그것으로 결과를 거둡니다. 답은 `status.message` 와 `artifacts` 양쪽에 있고, `metadata` 의 긴 URL 키는 이 플랫폼이 얹은 확장입니다(4장).

### 1.5 전제 조건

**A2A 요건이 아닙니다.** 아래는 1.1절의 *이 플랫폼이 만드는 모양*(모델 + 도구)을 따를 때의 전제입니다. 다른 모양으로 만든다면 해당 없고, 그래도 A2A 적합합니다.

| 전제 | 확인 방법 |
| --- | --- |
| 도구가 이미 호출 가능하게 노출돼 있습니다 | MCP·REST·DB — 무엇이든. 주소와 목록을 받아 둡니다 |
| 모델 엔드포인트가 있고 **도구 호출을 지원합니다** | 모델이 도구를 못 부르면 *이 모양*이 성립하지 않습니다 |
| 서비스를 띄울 호스트와 포트 | 배포 담당에게 받습니다 (5.7절) |

도구를 어떻게 부르든 A2A 의 관심이 아닙니다 — 밖으로 A2A 만 지키면 됩니다.

### 1.6 무엇을 만들면 되는가

**A2A 를 말하는 HTTP 서버 하나입니다.** 언어도, 웹 프레임워크도, 안에서 도구를 어떻게 부르는지도 자유입니다. 2장의 요건만 만족하면 됩니다.

```
   발화 → [ 당신의 에이전트 ] → 결과
              │
              ├─ 밖으로: A2A (2장·3장)          ← 이 문서가 정하는 것
              └─ 안으로: 모델·도구 (6장이 안내)   ← 당신이 정하는 것
```

| | |
| --- | --- |
| 최소 구현 | 엔드포인트 셋 — 5.1절 |
| 참고할 코드 | `reference/stub_agent.py` — 표준 라이브러리만으로 2장을 지킵니다 |
| 다 됐는지 확인 | `conformance_check.py` — 7장 |

**이미 만들어진 런타임 위에 설정만 얹는 방식**도 있습니다. 그런 배포물을 받았다면 그쪽 문서를 따르고, 이 문서는 **그 결과물이 지켜야 할 것**을 알려 줍니다.

### 1.7 이 문서의 예시에 대하여

설명에는 **상품 카탈로그·주문 에이전트**를 예시로 씁니다. 특정 업계에 속하지 않으면서 이 문서가 다뤄야 할 성질을 다 갖췄기 때문입니다.

- 조회(읽기 전용)와 주문(쓰기)이 함께 있다 → 병렬 실행 판단이 드러납니다(4.1.1절)
- 같은 이름의 상품이 여럿일 수 있다 → 되묻기가 자연스럽습니다(2.5절)
- 주문은 되돌리기 어렵다 → 되묻기 판단 축이 그대로 보입니다(6.7절)

**예시의 도구 이름·필드·업무 규칙은 그대로 쓰라는 뜻이 아니다.** 당신의 도메인으로 바꿉니다.

## 2. A2A 적합성 요건

**A2A Protocol v1.0 이 정한 것만** 여기 있습니다. 강도(MUST/SHOULD)는 전부 A2A 의 것이고, 절마다 규격의 몇 절인지 밝힙니다. 정본 사본이 `reference/` 에 있으니 의심되면 직접 대조하십시오.

이 절을 만족하면 **A2A 적합**합니다. 어느 조직의 오케스트레이터에도 붙습니다.

이 플랫폼이 추가로 정한 것(아티팩트 이름·확장·실패 보고 형식)은 **4장 프로파일**에 따로 있습니다. 그건 표준이 아니고, 안 따라도 여기 적합성에는 아무 영향이 없습니다.

### 2.1 필수 엔드포인트

엔드포인트는 1.3절의 흐름을 그대로 옮긴 것입니다. 경로와 메서드는 A2A 규격 11.3절이 정합니다.

| 하는 일 | 엔드포인트 |
| --- | --- |
| 이 에이전트가 무엇을 하는지 알립니다 | `GET /.well-known/agent-card.json` |
| 일을 시킵니다 | `POST /message:send` |
| 결과를 거둡니다 | `GET /tasks/{id}` |
| 그 밖 — 취소·목록·실시간·알림 | 아래 4~8 |

기준 URL 은 에이전트 카드가 선언한 `supportedInterfaces[0].url` 입니다.

A2A 규격 3.1절은 이것들을 **Core Operations** — *"모든 A2A 구현이 지원해야 하는 기본 능력"* — 으로 정의합니다. 그중 셋(스트리밍·푸시·확장 카드)만 카드의 `capabilities` 로 켜고 끌 수 있습니다(A2A 규격 3.3.4절).

| # | 메서드·경로 | 강도 | 비고 |
| --- | --- | --- | --- |
| 1 | `GET /.well-known/agent-card.json` | **MUST** | 없으면 발견 불가 (A2A 규격 8.2절) |
| 2 | `POST /message:send` | **MUST** | 없으면 부를 수 없습니다 |
| 3 | `GET /tasks/{id}` | **MUST** | 없으면 결과를 못 받습니다 |
| 4 | `GET /tasks` | **MUST** | Core Operation. 능력으로 끌 수 없습니다 |
| 5 | `POST /tasks/{id}:cancel` | **MUST** | Core Operation. 능력으로 끌 수 없습니다 |
| 6 | `POST /message:stream` | 조건부 | `capabilities.streaming` 이 `true` 면 **MUST**, 아니면 없어도 됩니다 |
| 7 | `/tasks/{id}:subscribe` | 조건부 | 위와 같습니다. 메서드는 아래 주의 참고 |
| 8 | `/tasks/{id}/pushNotificationConfigs` (POST·GET·DELETE) | 조건부 | `capabilities.pushNotifications` 가 `true` 면 **MUST** |

> **주의 — `:subscribe` 의 HTTP 메서드는 A2A 정본 안에서 어긋나 있습니다.**
>
> A2A 규격 11.3절(HTTP+JSON 바인딩)은 `POST /tasks/{id}:subscribe`, `a2a.proto` 는 `get: "/tasks/{id=*}:subscribe"` 입니다. 규격 자체의 불일치이고, 이 문서는 HTTP+JSON 바인딩 절(A2A 규격 11.3절)을 따라 **POST** 로 적었습니다. 붙을 상대와 맞춰야 하면 **둘 다 받는 편이 안전합니다.**
>
> 이런 이유로 정본은 **커밋을 못박아** 씁니다 — `reference/README.md` 에 커밋 해시가 있습니다.

**1·2·3 만으로도 오케스트레이터가 발견하고, 부르고, 결과를 받을 수 있습니다.** 다만 그것은 *상호운용의 최소치*이지 **A2A 적합의 최소치가 아닙니다** — 4·5 가 빠지면 Core Operation 이 빠진 것입니다.

선언과 구현이 어긋나면 안 됩니다 — `capabilities.streaming: false` 인데 `/message:stream` 을 부르면 `UnsupportedOperationError` **400** 을 **MUST** 돌려줍니다.

**Content-Type** — 요청·응답은 `application/a2a+json` **SHOULD**. 오류는 `application/problem+json` **MUST**.

### 2.2 프로토콜 버전 협상

버전은 `Major.Minor` 로만 가립니다 — 패치 번호는 호환에 영향을 주지 않고 요청·응답·카드에 **쓰지 않습니다**(A2A 규격 3.6절).

| 누가 | 무엇을 | 강도 |
| --- | --- | --- |
| 클라이언트 | 요청마다 `A2A-Version` 헤더를 보냅니다 | **MUST** |
| 클라이언트 | 헤더 대신 질의 파라미터(`?A2A-Version=1.0`)로 보내도 됩니다 | MAY |
| 에이전트 | 요청된 버전의 의미로 처리합니다 | **MUST** |
| 에이전트 | 지원하지 않는 버전이면 `VersionNotSupportedError` 를 냅니다 | **MUST** |
| 에이전트 | **빈 값은 `0.3` 으로 해석합니다** | **MUST** |
| 에이전트 | 같은 전송 방식에 버전이 다른 인터페이스를 여럿 열 수 있습니다 | MAY |

```http
POST /message:send HTTP/1.1
Host: agent.example.com
Content-Type: application/a2a+json
A2A-Version: 1.0
```

빈 값이 `0.3` 이 되는 규칙 때문에, **헤더를 아예 안 보는 구현은 모든 요청을 구버전으로 처리하게 됩니다.** 헤더를 읽고 모르는 버전이면 거절하는 것이 이 절의 요점입니다.

서비스 파라미터(`A2A-Version`·`A2A-Extensions`)는 HTTP 헤더로 전달합니다. 값이 여럿이면 쉼표로 잇습니다(A2A 규격 11.2절).

### 2.3 JSON 표현 규칙

| 규칙 | 강도 |
| --- | --- |
| 필드명은 **camelCase** (`contextId`, 아니라 `context_id`) — A2A 규격 5.5절 | **MUST** |
| enum 은 **대문자 문자열 이름 그대로** (`"TASK_STATE_WORKING"`) | **MUST** |
| 타임스탬프는 `YYYY-MM-DDTHH:mm:ss.sssZ` (UTC) — A2A 규격 5.6.1절 | **MUST** |
| `Z` 외의 시간대 오프셋 | **MUST NOT** |
| 설정하지 않은 선택 필드는 **생략** (`null` 로 채우지 않습니다) — A2A 규격 5.7절 | **SHOULD** |

### 2.4 에이전트 카드

**에이전트의 명함입니다.** 이름·설명·주소·할 수 있는 일을 담아 정해진 자리에 놓아 두면, 부르는 쪽이 그것만 읽고 붙습니다. 사전 합의가 필요 없는 이유가 이것입니다.

`GET /.well-known/agent-card.json` 이 **인증 없이** 200 과 함께 아래를 돌려줍니다(A2A 규격 8.2절).

**필수 8필드 — 하나라도 빠지면 부적합**

| 필드 | 타입 | 내용 |
| --- | --- | --- |
| `name` | string | 사람이 읽는 이름 |
| `description` | string | **라우팅의 핵심.** 6.2절 |
| `version` | string | 이 에이전트의 버전 |
| `supportedInterfaces` | array | 최소 1개. 2.4.1절 |
| `capabilities` | object | 2.4.2절 |
| `defaultInputModes` | string[] | 예: `["text/plain"]` |
| `defaultOutputModes` | string[] | 예: `["text/plain","application/json"]` |
| `skills` | array | 최소 1개. 2.4.3절 |

카드에 **`id` 필드는 없습니다.** 정체는 `name` + 인터페이스 URL 로 잡힙니다.

선택: `provider`(`{url, organization}` — 넣으면 둘 다 필수), `documentationUrl`, `securitySchemes`, `securityRequirements`, `signatures`, `iconUrl`.

#### 2.4.1 `supportedInterfaces`

```json
[{"url": "https://agent.example.com",
  "protocolBinding": "HTTP+JSON",
  "protocolVersion": "1.0"}]
```

`protocolBinding` 은 `"HTTP+JSON"` · `"JSONRPC"` · `"GRPC"` 중 하나. 이 문서는 **`"HTTP+JSON"` 만 다룹니다.** `url` 은 전체 URL 이고 경로 접두사를 포함해도 됩니다(`https://host/agents/catalog`).

첫 항목이 선호 인터페이스입니다.

#### 2.4.2 `capabilities`

```json
{"streaming": false,
 "pushNotifications": false,
 "extendedAgentCard": false,
 "extensions": [ … 4.1절 … ]}
```

**선언한 것은 반드시 구현합니다.** 안 할 거면 `false` 로 두는 것이 정직하고 적합합니다.

#### 2.4.3 `skills`

```json
{"id": "catalog_search",
 "name": "상품 검색",
 "description": "상품명·카테고리로 재고와 가격을 조회한다. 주문 생성은 이 스킬이 아니다.",
 "tags": ["상품", "재고", "가격"],
 "examples": ["파란색 머그컵 재고 있어?", "A-1023 가격 얼마야"]}
```

| 필드 | 강도 |
| --- | --- |
| `id` · `name` · `description` · `tags` | **MUST** |
| `examples` · `inputModes` · `outputModes` · `securityRequirements` | MAY |

**`AgentSkill` 에는 입력 스키마가 없습니다.** 스킬은 호출 시그니처가 아니라 **오케스트레이터가 읽고 어디로 보낼지 고르는 설명문**입니다. 호출구는 언제나 `POST /message:send` 하나입니다. 스킬을 나눈다고 엔드포인트가 늘지 않습니다.

### 2.5 태스크 상태 기계

Task 는 아무 상태로나 옮겨 다니지 않습니다. **한 번 끝난 일은 되살아나지 않고, 되묻는 중인 일은 답을 받으면 다시 돌아갑니다** — 이 두 규칙이 아래 그림의 전부입니다.

```
   POST /message:send  (taskId 없음)
             │
             ▼
       SUBMITTED ──────────► WORKING ──┬──► COMPLETED   종결
             │                   ▲     ├──► FAILED      종결
             │                   │     ├──► CANCELED    종결
             ▼                   │     └──► INPUT_REQUIRED   중단
        REJECTED                 │                │
         종결                    └────────────────┘
                     POST /message:send  (taskId = 그 태스크)
```

| 상태 | 성격 | 뜻 |
| --- | --- | --- |
| `TASK_STATE_SUBMITTED` | 진행 | 접수됨 |
| `TASK_STATE_WORKING` | 진행 | 처리 중 |
| `TASK_STATE_COMPLETED` | **종결** | 성공 |
| `TASK_STATE_FAILED` | **종결** | 실패 |
| `TASK_STATE_CANCELED` | **종결** | 취소됨 |
| `TASK_STATE_REJECTED` | **종결** | 수행 거절 |
| `TASK_STATE_INPUT_REQUIRED` | **중단** | 추가 입력 필요. 재개 가능 |
| `TASK_STATE_AUTH_REQUIRED` | **중단** | 인증 필요. 재개 가능 |
| `TASK_STATE_UNSPECIFIED` | — | 쓰지 않습니다 |

**종결 상태에서는 되돌아올 수 없습니다. 중단 상태는 메시지를 더 받으면 `WORKING` 으로 돌아옵니다.**

#### 필수 거절 넷

| 상황 | 오류 | HTTP |
| --- | --- | --- |
| 종결 태스크에 메시지 — A2A 규격 3.1.1절 | `UnsupportedOperationError` | 400 |
| 종결 태스크에 `:cancel` — A2A 규격 3.1.5절 | `TaskNotCancelableError` | 400 |
| 종결 태스크에 `:subscribe` — A2A 규격 3.1.6절 | `UnsupportedOperationError` | 400 |
| `contextId` 와 `taskId` 가 서로 안 맞음 — A2A 규격 3.4.3절 | `UnsupportedOperationError` | 400 |
| 없는 `taskId` | `TaskNotFoundError` | 404 |

#### 식별자 규칙

| 규칙 | 강도 |
| --- | --- |
| `taskId` 는 **서버가 만듭니다.** 클라이언트 지정은 지원하지 않습니다 | **MUST** |
| `contextId` 도 서버가 만드는 것이 기본. 클라이언트가 준 값을 받아도 됩니다 | MAY |
| 클라이언트가 준 `contextId` 를 못 받으면 **거절**합니다. 새로 만들어 주지 않습니다 | **MUST** |
| 클라이언트는 서버가 만든 `contextId` 를 **불투명한 문자열**로 다룹니다. 구조를 가정하지 않습니다 | **SHOULD** |

`contextId` 를 만드는 것은 **각 에이전트**입니다. 오케스트레이터가 두 에이전트를 부르면 각자에게서 값을 받고, **그 둘이 같다는 보장도 다르다는 보장도 없습니다** — A2A 는 그것을 말하지 않습니다.

그래서 부르는 쪽은 **에이전트별 이름공간으로** 다뤄야 합니다. 이건 규격이 정한 것이 아니라 안전한 취급 방식이고, 이 플랫폼이 그렇게 합니다(4.4절).

### 2.6 되묻기와 재개

정보가 부족하면 **되묻습니다.** 지어내지 않습니다.

```
① 클라이언트 → 에이전트
   POST /message:send
   {"message": {"messageId": "<uuid>", "role": "ROLE_USER",
                "parts": [{"text": "머그컵 주문해줘"}]},
    "configuration": {"returnImmediately": true}}
   ← 200 {"task": {"id": "T1", "contextId": "C1",
                   "status": {"state": "TASK_STATE_SUBMITTED"}}}

② 클라이언트가 폴링
   GET /tasks/T1
   ← {"id": "T1", "contextId": "C1",
      "status": {"state": "TASK_STATE_INPUT_REQUIRED",
                 "message": {"messageId": "<uuid>", "role": "ROLE_AGENT",
                             "taskId": "T1", "contextId": "C1",
                             "parts": [{"text": "머그컵이 3종 있습니다. 어느 것입니까?"}]},
                 "timestamp": "2026-09-01T12:00:03.100Z"},
      "artifacts": [{"artifactId": "T1:candidates", "name": "candidates",
                     "parts": [{"mediaType": "application/json",
                                "data": [{"sku": "A-1023", "label": "파란 머그컵 350ml"},
                                         {"sku": "A-1024", "label": "흰 머그컵 350ml"},
                                         {"sku": "B-2001", "label": "보온 머그컵 400ml"}]}]}]}

③ 클라이언트 → 에이전트 (같은 태스크를 이어서)
   POST /message:send
   {"message": {"messageId": "<uuid>", "role": "ROLE_USER",
                "taskId": "T1", "contextId": "C1",
                "parts": [{"text": "파란 거"}]}}
   → T1 이 WORKING 으로 복귀. 새 태스크가 아니다.
```

| 규칙 | 강도 |
| --- | --- |
| 되물을 때 `status.message` 에 **질문을 담습니다** | **MUST** |
| 그 메시지의 `role` 은 `ROLE_AGENT`, `taskId`·`contextId` 를 채웁니다 | **MUST** |
| 재개 메시지는 `taskId` 를 싣습니다 | **MUST** |
| `contextId` 는 함께 실어도 되고 빼도 됩니다 — 빼면 **에이전트가 태스크에서 추론합니다** | MAY |
| 둘 다 실었으면 **서로 맞아야 합니다** (안 맞으면 거절) | **MUST** |

**A2A 가 정하는 것은 여기까지입니다.** 후보를 무엇에 어떤 모양으로 실을지는 정하지 않습니다 — 이 플랫폼은 `candidates` 아티팩트로 정했고, 그건 4.2절에 있습니다. 재개할 때 무엇을 들고 있어야 하는지도 A2A 는 말하지 않습니다 — 5.9절에서 다룹니다.

### 2.7 오류 응답

본문은 `application/problem+json` (RFC 9457). 아래 매핑은 A2A 규격 5.4절의 표 그대로입니다.

```json
{"type": "https://a2a.dev/errors/TaskNotFoundError",
 "title": "TaskNotFoundError",
 "status": 404,
 "detail": "모르는 태스크입니다: T9"}
```

| --- | --- |
| `TaskNotFoundError` | **404** |

| `ContentTypeNotSupportedError` | 400 |

| `ExtensionSupportRequiredError` | 400 |
| `VersionNotSupportedError` | 400 |

## 3. 데이터 모델 — 필드 사전

1.3절의 네 개념이 실제로 어떤 필드를 갖는지 모아 둔 **찾아보는 절**입니다. 처음부터 읽을 필요는 없고, 구현하다 막힐 때 폅니다.

**R** = 필수(A2A 가 `REQUIRED` 로 표시한 것), `Struct` = 임의의 JSON 객체.

직접 구현할 때 필요합니다. 샘플 런타임을 쓴다면 런타임이 처리하므로 건너뛰어도 됩니다.

### 3.1 `Task`

| 필드 | 타입 | R | 뜻 |
| --- | --- | :-: | --- |
| `id` | string | R | 서버 생성 |
| `contextId` | string | | 이 태스크가 속한 대화 |
| `status` | TaskStatus | R | |
| `artifacts` | Artifact[] | | 산출물 (4.2절) |
| `history` | Message[] | | 주고받은 메시지 |
| `metadata` | Struct | | 확장이 여기 삽니다 (4.1.2절) |

`TaskStatus` = `state`(TaskState, R) · `message`(Message) · `timestamp`(ISO8601)

### 3.2 `Message`

| 필드 | 타입 | R | 뜻 |
| --- | --- | :-: | --- |
| `messageId` | string | R | 보내는 쪽이 만듭니다(UUID) |
| `contextId` | string | | 대화 지정 |
| `taskId` | string | | 있으면 **그 태스크를 이어서** |
| `role` | Role | R | `ROLE_USER`(클라이언트→서버) / `ROLE_AGENT`(서버→클라이언트) |
| `parts` | Part[] | R | 내용 |
| `metadata` | Struct | | |
| `extensions` | string[] | | 이 메시지가 쓰는 확장 URI |
| `referenceTaskIds` | string[] | | 참조하는 다른 태스크 |

### 3.3 `Part` — 넷 중 하나만

| 필드 | 타입 | 뜻 |
| --- | --- | --- |
| `text` | string | 평문 |
| `raw` | bytes(base64) | 인라인 바이너리 |
| `url` | string | 외부 참조 |
| `data` | any JSON | 구조화 산출물 |
| `metadata` | Struct | |
| `filename` | string | |
| `mediaType` | string | 예: `application/json` |

### 3.4 `Artifact`

`artifactId`(string, R) · `name`(string) · `description`(string) · `parts`(Part[], R) · `metadata`(Struct) · `extensions`(string[])

### 3.5 요청·응답

| 타입 | 필드 |
| --- | --- |
| `SendMessageRequest` | `message`(R) · `configuration` · `metadata` · `tenant` |
| `SendMessageConfiguration` | `acceptedOutputModes[]` · `historyLength` · **`returnImmediately`**(bool) · `taskPushNotificationConfig` |
| `SendMessageResponse` | oneof: `task` \| `message` |
| `GetTaskRequest` | `id`(R) · `historyLength` · `tenant` |
| `CancelTaskRequest` | `id`(R) · `metadata` · `tenant` |
| `ListTasksRequest` | `contextId` · `status` · `pageSize`(1~100) · `pageToken` · `historyLength` · `statusTimestampAfter` · `includeArtifacts` |
| `ListTasksResponse` | `tasks[]`(R) · `nextPageToken`(R) · `pageSize`(R) · `totalSize`(R) |

**`returnImmediately`**

| 값 | 동작 |
| --- | --- |
| `true` | 태스크만 만들고 **즉시 반환.** 클라이언트가 `GET /tasks/{id}` 로 폴링 (A2A 규격 3.2.2절) |
| `false` 또는 없음 | 종결·중단 상태에 닿을 때까지 **막고 기다린다** |

둘 다 **MUST** 지원합니다. 오케스트레이터는 보통 `true` 를 씁니다.

### 3.6 스트리밍 (`capabilities.streaming: true` 일 때만)

`Content-Type: text/event-stream`. `data:` 한 줄에 하나의 JSON. oneof 키가 그대로 JSON 키가 됩니다.

```
data: {"task":{"id":"T1","contextId":"C1","status":{"state":"TASK_STATE_WORKING"}}}

data: {"artifactUpdate":{"taskId":"T1","contextId":"C1","artifact":{"artifactId":"T1:answer","name":"answer","parts":[{"text":"재고 12개 있습니다."}]},"lastChunk":true}}

data: {"statusUpdate":{"taskId":"T1","contextId":"C1","status":{"state":"TASK_STATE_COMPLETED"}}}
```

| 규칙 | 강도 |
| --- | --- |
| 스트림은 **`Task` 객체로 시작**합니다 — A2A 규격 3.1.2절 | **MUST** |
| 이벤트는 **생성 순서를 지킵니다.** 재정렬 금지 | **MUST** |
| **종결** 상태에 닿으면 스트림을 닫습니다 — `COMPLETED`·`FAILED`·`CANCELED`·`REJECTED` | **MUST** |
| `INPUT_REQUIRED` 는 닫는 조건이 **아니다.** 되묻기 왕복이 같은 스트림에서 이어집니다 | — |
| 한 태스크에 동시 스트림 여럿을 허용합니다 | MAY |
| 동시 스트림이 있으면 **모두 같은 이벤트를 같은 순서로** 받습니다 | **MUST** |
| 하나를 닫아도 나머지와 태스크는 영향받지 않습니다 | **MUST** |

중단 상태에서 스트림을 열어 두면 아무도 답하지 않을 때 연결이 샙니다. **무응답 시한**을 두는 것은 규격이 금지하지 않는 구현 선택이고, 두는 편이 낫습니다.

`TaskStatusUpdateEvent` = `taskId`(R) · `contextId`(R) · `status`(R) · `metadata`
`TaskArtifactUpdateEvent` = `taskId`(R) · `contextId`(R) · `artifact`(R) · `append` · `lastChunk` · `metadata`

### 3.7 푸시 알림 (`capabilities.pushNotifications: true` 일 때만)

```
POST   /tasks/{id}/pushNotificationConfigs            {"url": "...", "token": "..."}
GET    /tasks/{id}/pushNotificationConfigs
GET    /tasks/{id}/pushNotificationConfigs/{configId}
DELETE /tasks/{id}/pushNotificationConfigs/{configId}
```

`TaskPushNotificationConfig` = `id` · `taskId` · **`url`(R)** · `token` · `authentication`(`{scheme, credentials}`) · `tenant`

웹훅은 프로토콜 바인딩과 무관하게 **평범한 HTTP POST 에 이 문서의 JSON** 을 싣습니다. `token` 은 수신 측이 진위를 확인하도록 그대로 되돌려 줍니다.

## 4. 이 플랫폼의 프로파일 — 표준이 아니다

**여기 있는 것은 A2A 가 정한 것이 아니다.** 이 플랫폼이 A2A 가 비워 둔 자리를 채운 관례이고, 우리 오케스트레이터가 이 약속을 읽습니다.

| | |
| --- | --- |
| **안 따라도** | A2A 적합합니다. 2장만 만족하면 어느 오케스트레이터에도 붙습니다 |
| **따르면** | 이 플랫폼의 부가 기능을 씁니다 — 병렬 실행 판단, 진행률·토큰 보고, 구조화된 되묻기·실패 보고 |
| **다르게 정해도** | 됩니다. 다만 그때는 이 프로파일이 아니라 **당신 조직의 프로파일**이고, 부르는 쪽과 같은 약속을 공유해야 합니다 |

아래 강도 표현은 **이 프로파일 안에서만** 뜻이 있습니다. "프로파일을 따른다면 MUST" 이지 "A2A 적합하려면 MUST" 가 아니다.

**A2A 는 이런 확장을 예상하고 만들어졌습니다.** 확장은 URI 로 식별되고 `required: false` 로 선언되므로, 모르는 클라이언트는 그냥 무시하고 정상 동작합니다 — 그래서 프로파일을 얹어도 표준 적합성이 깨지지 않습니다(A2A 규격 3.3절).

### 4.1 확장 셋

A2A 에 없는 개념 셋을 `capabilities.extensions[]` 에 **선언합니다.** 선언하면 상대가 카드만 읽고 무엇이 오는지 압니다.

셋 다 `required: false` 다 — **모르는 클라이언트는 무시하고 정상 동작합니다.**

> ### ⚠ 먼저 정할 것 — 확장 URI 의 도메인
>
> 아래 `<도메인>` 은 **이 프로파일을 쓰는 조직이 정합니다.** 소유한 도메인을 쓰세요.
>
> - 이 플랫폼에 **붙이려는** 것이면 → 그 플랫폼이 공표한 URI 를 그대로 씁니다. 배포처에 물어보세요.
> - **자기 프로파일**을 만드는 것이면 → 자기 도메인으로 정합니다. 그건 이 프로파일과 별개의 확장입니다.
>
> **정하지 않고 예시 값을 그대로 쓰면 안 됩니다.** URI 가 다르면 서로 다른 확장이고, 상대가 못 읽습니다. 오류는 안 납니다 — 그냥 무시됩니다.

| URI | 어디에 실리나 | 강도 |
| --- | --- | --- |
| `https://<도메인>/ext/tool-hints/v1` | 카드의 `params` | **SHOULD** — 빼면 병렬 실행이 죽습니다 |
| `https://<도메인>/ext/progress/v1` | `Task.metadata` | MAY |
| `https://<도메인>/ext/usage/v1` | `Task.metadata` | MAY |

**한 번 정하면 설정이 아니라 상수입니다.** A2A 가 확장을 URI 로 식별하게 한 이유가 URI 자체가 계약이기 때문입니다 — 카드에 이 값이 실려 오면 아는 쪽은 읽고 모르는 쪽은 무시합니다. 환경변수로 두면 양쪽이 밖에서 값을 맞춰야 하고, 그 순간 확장이 아니라 **두 당사자의 사설 관례**가 됩니다.

#### 4.1.1 `tool-hints` — 병렬 실행 판단

`AgentSkill` 에는 부작용을 밝힐 자리가 없습니다. 그래서 확장으로 싣습니다.

```json
{"uri": "https://<도메인>/ext/tool-hints/v1",
 "description": "스킬별 실행 힌트. 호출자의 스케줄러가 병렬 가능 여부를 판단한다.",
 "required": false,
 "params": {"skills": {
   "catalog_search": {"readOnly": true,  "destructive": false, "idempotent": true},
   "order_place":    {"readOnly": false, "destructive": false, "idempotent": false}}}}
```

**오케스트레이터의 집계 규칙 — 보수적입니다.**

```
모든 스킬이 readOnly:true  →  이 에이전트는 읽기 전용. 다른 읽기와 병렬로 돈다
하나라도 readOnly:false    →  쓰기. 다른 쓰기와 직렬로 돈다
확장 선언이 없다           →  쓰기로 취급
```

어느 스킬이 쓰일지 부르기 전에 알 수 없어서 그렇입니다. **읽기만 하는 에이전트라면 반드시 선언하십시오** — 안 하면 병렬 실행에서 빠지는데 **오류가 안 납니다.** 결과는 맞게 나오고 느려질 뿐이라 테스트로도 안 잡힙니다.

#### 4.1.2 `progress` · `usage` — `Task.metadata`

```json
{"metadata": {
  "https://<도메인>/ext/progress/v1": {"fraction": 0.6, "message": "재고 조회 중"},
  "https://<도메인>/ext/usage/v1":    {"tokensIn": 4210, "tokensOut": 118}}}
```

`fraction` 은 0.0~1.0. `usage` 는 이 태스크가 쓴 모델 토큰입니다 — **에이전트가 보고하지 않으면 아무도 못 봅니다.** 오케스트레이터는 자기 호출 한 번만 세기 때문입니다.


### 4.2 아티팩트 규약

A2A 는 `Artifact` 라는 그릇만 정하고 무엇을 담을지는 정하지 않습니다. 이 플랫폼은 **이름으로** 정합니다.

| `name` | `parts[0]` | 언제 | 강도 |
| --- | --- | --- | --- |
| `answer` | `text` | 언제나 | **MUST** |
| `actions` | `data` (`mediaType: application/json`) | 화면에 그릴 것이 있을 때 | MAY |
| `candidates` | `data` | 되묻기에서 후보를 줄 때 | 되묻기를 하면 **SHOULD** |
| `resolve` | `data` | 되묻기의 구조화 형태 | MAY |
| `facts` | `data` | 도구가 밝힌 사실을 부르는 쪽이 이어 써야 할 때 | MAY |
| `errors` | `data` | 실패한 도구가 있을 때 | 4.3절 |

#### `candidates` 의 모양

이름 규약만으로는 부족한 자리입니다. 되묻기가 닫히려면 부르는 쪽이 후보를 **화면에 그리고 사용자의 선택을 되돌려 보낼 수 있어야** 합니다.

`parts[0].data` 는 객체의 **목록**이고, 각 객체는 둘을 갖습니다.

| 필드 | 타입 | 뜻 | 강도 |
| --- | --- | --- | --- |
| 식별자 | string | 이 후보를 **유일하게** 가리키는 값. 이름은 도메인이 정합니다(`sku`·`id`·`code`…) | **MUST** |
| 표시 | string | 사람이 읽고 **서로 구별할 수 있는** 문자열 | **MUST** |
| 그 밖 | any | 화면에 필요한 부가 정보 | MAY |

```json
{"artifactId": "t1:candidates", "name": "candidates",
 "parts": [{"mediaType": "application/json",
            "data": [{"sku": "A-1023", "label": "파란 머그컵 350ml"},
                     {"sku": "A-1024", "label": "흰 머그컵 350ml"}]}]}
```

두 후보의 **표시가 같으면 안 됩니다.** 사용자가 골라도 어느 것인지 구별되지 않아 루프가 닫히지 않습니다 — 실측에서 통과율 0% 를 만든 원인입니다.

- `artifactId` 는 `{taskId}:{name}` 형식을 **SHOULD** 씁니다. 폴링 클라이언트가 이름으로 대조하기 쉽습니다.
- `answer` 의 텍스트는 `status.message` 에도 같이 실어 **SHOULD** 줍니다. 아티팩트를 안 읽는 클라이언트도 답을 볼 수 있습니다.
- 여기 없는 이름을 **MAY** 추가합니다. 모르는 이름을 받은 클라이언트는 무시합니다.

**`actions` 의 명령 어휘는 이 규격이 정하지 않습니다.** 그건 결과를 소비하는 화면과의 계약입니다. 화면이 없는 도메인이면 이 아티팩트를 쓰지 않습니다.

#### `facts` 의 모양

`parts[0].data` 는 **{이름: 값}** 객체입니다. 이름은 도메인이 정하고(`parcel`·`pnu`·`address`…), 부르는 쪽은 그 뜻을 해석하지 않고 **자리로만** 씁니다 — 다음 호출에 그대로 되돌려 주기 위해서입니다.

여러 턴에 걸친 대화에서 필요합니다. 답 문장에만 있는 값은 부르는 쪽이 다시 쓸 수 없어, 다음 턴이 같은 대상을 다시 묻거나 다시 찾습니다(실측 2026-09-14: 멀티턴 60턴 중 9턴이 대상을 몰라 되묻고 빈손으로 끝났습니다).

- **값은 작게 싣습니다.** 도형 원문(WKT)·이미지·업스트림 응답 전체는 넣지 않습니다. 그건 `resolve` 나 화면용 자리의 몫입니다.
- **이번 턴에 사실이 없으면 빈 객체로 올립니다.** 지난 턴의 사실이 남아 다음 턴이 엉뚱한 대상을 이어 쓰는 것을 막습니다.


### 4.3 실패 규약

A2A 는 실패의 *내용*을 정하지 않습니다. `TASK_STATE_FAILED` 의 설명은 "오류로 끝났습니다" 한 줄이고, 부분 실패를 표현할 자리도 없습니다. 이 절이 그 빈 곳을 채웁니다.

#### 원칙 — 자기 도메인은 자기가 처리하고, 못 하면 보고한다

```
내부 오류(도구 실패 등)
   │
   ├─① 에이전트가 스스로 처리한다 — 인자를 고쳐 재시도, 다른 도구로 우회
   │     N회(권장 2) 안에 풀리면 밖에 안 보인다
   │
   └─② N회를 써도 안 되면 오케스트레이터에 보고한다
```

①을 건너뛰고 모든 오류를 위로 올리면 에이전트의 존재 이유가 사라집니다. 오케스트레이터는 당신의 도메인을 모릅니다.

#### 보고 모양 셋

| 상황 | 상태 | `status.message` | `artifacts` |
| --- | --- | --- | --- |
| 사용자가 정보를 줘야 진행 가능 | `TASK_STATE_INPUT_REQUIRED` | 되묻는 질문 | `candidates` |
| 답은 만들어졌고 일부만 빠짐 | `TASK_STATE_COMPLETED` | 답 + 무엇이 빠졌는지 | 정상 + **`errors`** |
| 답을 못 만듦 | `TASK_STATE_FAILED` | **사람이 읽을 실패 사유** | 부분 결과라도 남깁니다 |

`status.message` 에 "실패했습니다"만 적는 것은 **SHOULD NOT**. 규격이 오류에 대해 요구하는 것은 *actionable information* 입니다 — 무엇이 왜 안 됐고 무엇을 하면 되는지 적습니다.

#### 재시도하지 않는 경우

**의존 서비스에 아예 닿지 못하면 재시도하지 않고 즉시 보고합니다.** 몇 번을 다시 불러도 같고, 재시도 한 번이 모델 호출 한 번입니다.

**"도구가 안 된다고 했다"와 "도구가 거기 없습니다"를 가릅니다.** 앞은 고칠 여지가 있고 뒤는 없습니다.

#### `errors` 아티팩트

문자열이 아니라 구조로 싣습니다 — 오케스트레이터의 **모델이 읽고** 다른 에이전트로 우회할지 판단합니다.

```json
{"artifactId": "T1:errors", "name": "errors",
 "parts": [{"mediaType": "application/json",
            "data": [{"tool": "inventory_lookup",
                      "kind": "tool_error",
                      "message": "상품 코드가 필요합니다. sku 또는 name 중 하나를 지정하세요.",
                      "recoverable": true,
                      "attempts": 2}]}]}
```

| 필드 | 값 |
| --- | --- |
| `tool` | 실패한 것의 이름. 내부 이름이어도 됩니다 |
| `kind` | `"tool_error"`(대상이 실패를 보고) 또는 `"unavailable"`(대상에 못 닿음) |
| `message` | 사람이 읽을 수 있는 사유 |
| `recoverable` | 재시도로 풀릴 여지가 있었는지. `unavailable` 이면 언제나 `false` |
| `attempts` | 시도 횟수 |

---

### 4.4 같은 컨텍스트의 이전 태스크를 어떻게 다루나

A2A 는 `contextId` 를 "여러 태스크를 묶는 대화 단위"라고만 정하고, 에이전트가 그 이전 태스크들을 **어떻게 써야 하는지는 정하지 않습니다.** 그래서 둘째 턴에서 완전히 다르게 행동하는 두 구현이 양쪽 다 적합할 수 있습니다. 대화형 제품에서는 이 빈칸이 큽니다.

이 플랫폼은 이렇게 정합니다.

- 같은 `contextId` 의 **종결된 이전 태스크를 참조할 수 있어야 합니다**(SHOULD). `"아까 그거 주문해줘"` 가 성립하려면 필요합니다.
- 참조 범위는 **에이전트가 정하고 카드에 밝힙니다**(MAY) — 최근 N개, 최근 M분, 또는 참조 안 함. 밝히지 않으면 참조하지 않는 것으로 봅니다.
- **재개(`taskId` 가 있는 메시지)와 혼동하지 않습니다.** 재개는 그 태스크를 이어가는 것이고, 컨텍스트 참조는 새 태스크가 이전 것을 읽는 것입니다.
- 컨텍스트에 만료·정리 정책을 두면 **문서로 밝힙니다**(A2A 규격 3.4.1절이 SHOULD 로 요구).

참조하지 않기로 하는 것도 적합합니다. **밝히지 않는 것이 문제다** — 부르는 쪽이 둘째 턴의 동작을 예측할 수 없습니다.

## 5. 직접 구현하기

언어는 자유입니다. **2장를 만족하면 적합합니다.** 3장이 데이터 모델 전체입니다.

### 5.1 첫 단계 구현 — 핵심 세 엔드포인트

```
GET  /.well-known/agent-card.json    카드를 그대로 돌려준다 (2.3절)
POST /message:send                   태스크를 만들고 즉시 반환, 뒤에서 처리
GET  /tasks/{id}                     현재 상태를 돌려준다
```

이 셋이면 오케스트레이터가 발견하고, 부르고, 결과를 받습니다. 나머지는 나중에 더합니다.

### 5.2 처리 흐름

```
POST /message:send 수신
  │
  ├─ message.taskId 가 있나?
  │    있음 → 그 태스크를 찾는다
  │            없으면          → TaskNotFoundError 404
  │            종결 상태면      → UnsupportedOperationError 400
  │            contextId 불일치 → UnsupportedOperationError 400
  │            중단 상태면      → WORKING 으로 되돌리고 이어서 처리
  │    없음 → 새 taskId 생성. contextId 는 주어진 것을 쓰거나 새로 만든다
  │
  ├─ 상태를 SUBMITTED → WORKING
  │
  ├─ configuration.returnImmediately 가 true 인가?
  │    true  → 지금 Task 를 반환. 처리는 백그라운드에서 계속
  │    false → 종결·중단 상태에 닿을 때까지 기다렸다가 반환
  │
  └─ 처리 (당신의 도메인 로직)
       ├─ 성공          → 아티팩트 채우고 COMPLETED
       ├─ 정보 부족      → status.message 에 질문, candidates 아티팩트, INPUT_REQUIRED
       ├─ 부분 실패      → 답 + errors 아티팩트, COMPLETED
       ├─ 실패          → status.message 에 사유, FAILED
       └─ 내 일이 아님    → REJECTED
```

### 5.3 카드를 손으로 유지하지 않는다

2.4.2절가 "선언한 것은 반드시 구현합니다"를 **MUST** 로 두는데, 경로 B 에서 카드가 손으로 쓴 JSON 이면 **핸들러와 구조적으로 묶여 있지 않습니다.** 갈라지는 것이 기본값이 됩니다 — 스트리밍을 껐는데 카드는 `true` 로 남고, 스킬을 지웠는데 카드에는 있고.

**라우트를 등록하는 그 자료구조에서 카드를 생성합니다.** 한 곳에서만 선언하면 갈라질 자리가 없습니다.

```
선언 (한 곳)
  ├─ 라우트 등록      → 실제 핸들러
  └─ 카드 생성        → /.well-known/agent-card.json
```

최소한 **테스트로 묶습니다** — 카드가 `streaming: true` 라고 하면 `/message:stream` 이 400 이 아닌지 확인하는 테스트 하나면 갈라짐을 잡습니다. `conformance_check.py` 가 이 대조를 하지만, 그건 배포 직전이지 개발 중이 아니다.

### 5.4 상태를 바꾸는 코드는 한 군데로 모읍니다

전이 검증(2.4절)을 한 함수 안에서만 하면 적합성을 테스트로 지킬 수 있습니다. 상태 변경이 코드 곳곳에 흩어지면 반드시 어딘가에서 규칙이 깨집니다.

```
transition(taskId, newState, message=None)
  현재 상태 조회
  (현재, 새 상태) 가 합법 전이인가? 아니면 예외
  상태·메시지·timestamp 갱신
  스트리밍을 지원하면 statusUpdate 이벤트 방송
```

### 5.5 태스크 저장

메모리에 두어도 **적합합니다.** 재시작하면 진행 중 태스크를 잃는데, 그때 `TaskNotFoundError` 404 를 정직하게 내면 규격을 지킨 것입니다. 클라이언트는 그것을 "모릅니다"로 처리합니다.

**종결 태스크는 정리해야 합니다.** 안 하면 무한히 쌓입니다. TTL(예: 1시간)과 개수 상한(예: 1000)을 둡니다.

### 5.6 흔한 구현 실수

| 실수 | 결과 |
| --- | --- |
| `context_id` 처럼 snake_case 로 직렬화 | 클라이언트가 필드를 못 읽습니다. 조용히 빈 값 |
| `"state": "working"` 처럼 소문자 | 상태 파싱 실패 |
| 타임스탬프에 `+09:00` | 규격 위반. 파서에 따라 실패 |
| 설정 안 한 필드를 `null` 로 채움 | 서명·정규화가 필요할 때 깨집니다 |
| `taskId` 를 클라이언트가 정하게 함 | 규격 위반 |
| 종결 태스크에 온 메시지를 새 태스크로 처리 | 조용히 이력이 갈라집니다 |
| `capabilities.streaming: true` 인데 미구현 | 클라이언트가 스트리밍을 시도하다 실패 |
| `A2A-Version` 헤더를 안 봄 | 빈 값이 `0.3` 으로 해석되므로 **모든 요청을 구버전으로 처리**하는 셈이 됩니다 (2.2절) |
| 되묻기 후보에 구별 불가능한 값 | 루프가 안 닫힙니다 |
| **재개에서 이전 상태를 안 들고 있음** | 답을 새 질의로 읽고 같은 질문을 반복합니다(2.5절). 형식 검사는 전부 통과하므로 왕복을 돌려 봐야 잡힙니다 |
| 카드를 손으로 유지 | 선언과 구현이 갈라집니다(6.3절) |

### 5.7 포트 고르기

포트 배정은 배포마다 다릅니다. 규칙만 적습니다.

- **한 호스트에 여러 프로젝트가 사는 경우가 흔합니다.** 다른 스택이 쓰는 대역을 먼저 확인하고 침범하지 않습니다. 남의 프로세스를 죽이는 사고는 대부분 여기서 시작합니다.
- 에이전트는 **연속된 대역에서 다음 빈 번호**를 씁니다. 방화벽·프록시 규칙을 대역 단위로 쓸 수 있습니다.
- 띄우기 전에 비었는지 확인합니다. 환경에 있는 것을 씁니다 — `ss` 가 없는 컨테이너가 흔합니다.

  ```bash
  ss -ltn | grep :<포트>          # iproute2
  netstat -ltn | grep :<포트>     # net-tools
  lsof -i :<포트>                 # lsof
  curl -s -o /dev/null localhost:<포트> && echo "이미 쓰는 중"   # 아무것도 없을 때
  ```
- **정한 번호를 배포 문서에 적습니다.** 안 적으면 다음 사람이 같은 번호를 고릅니다.

### 5.8 모델을 부르는 에이전트에서 실제로 큰 것 둘

#### 추론 강도 (`reasoning_effort` 계열)

추론형 모델은 **추론을 끌 수 없고 세기만 조절됩니다.** 값을 주지 않으면 꺼지는 것이 아니라 모델 기본값(대개 높음)으로 돕니다. 직관과 반대라 자주 놓칩니다.

| 설정 | 단일 호출 실측 | |
| --- | --- | --- |
| 미설정 | 5.9초 | 312 토큰 |
| `medium` | 2.2초 | 184 토큰 |
| `low` | **1.1초** | **92 토큰** |

턴 전체로는 14.8초 → 5.1초였습니다. **도구를 부르는 에이전트에는 `low` 가 대개 맞습니다** — 어려운 추론은 도구가 하고 모델은 고르기만 합니다.

#### 도구 결과 절단 상한

도구 응답이 길면 그 하나가 모델 컨텍스트를 잠식해 **모델이 성공한 조회를 "실패했습니다"고 답합니다.** 실측 사례에서 한 응답이 21,519자였습니다.

런타임은 **모델에 넣는 문자열만** 자르고, 원본은 그대로 두어 아티팩트 성형에 씁니다. 자른 사실을 문장으로 밝혀 모델이 "값이 없습니다"와 "값이 잘렸습니다"를 구별하게 합니다.

### 5.9 재개 — 왕복을 가로질러 무엇이 살아남아야 하나

프로토콜 껍데기는 쌉니다. 어려운 것은 여깁니다. **"이어서 처리합니다"는 한 단어 안에 이 규격에서 가장 많은 구현 비용이 들어 있습니다.**

재개 메시지는 그 자체로는 뜻이 없습니다. `"파란 거"` 나 `"첫 번째"` 는 **직전에 무엇을 물었고 어떤 후보를 줬는지**를 알아야만 해석됩니다. 그 상태를 안 들고 있으면 에이전트는 재개 메시지를 새 질의로 읽고, 같은 질문을 다시 하고, 루프가 닫히지 않습니다 — 실측 사례에서 조회 계열 네 그룹의 통과율이 0% 였던 원인이 정확히 이것입니다.

A2A 는 `taskId` 로 태스크를 이어가라고만 하고 **무엇을 보존하라는 말은 하지 않습니다.** 그런데 보존하지 않으면 '이어가는' 것이 성립하지 않습니다. 아래는 그 요건이고, 강도는 A2A 가 아니라 이 안내서의 것입니다.

**`taskId` 가 재개의 열쇠입니다.** 그 하나로 아래를 되찾을 수 있어야 합니다.

| 무엇 | 강도 | 없으면 |
| --- | --- | --- |
| **원래 요청** — 태스크를 연 발화 | **MUST** | 무엇을 하려던 것인지 모릅니다 |
| **직전에 한 질문** | **MUST** | 같은 질문을 반복합니다 |
| **제시한 후보 목록**(냈다면) | **MUST** | `"첫 번째"`·`"파란 거"` 를 해석할 수 없습니다 |
| 이미 받은 도구 결과 | **SHOULD** | 같은 조회를 다시 합니다 — 시간·비용·라운드 상한 |
| 모델 대화 상태 | **SHOULD** | 맥락을 잃고 답이 얕아집니다 |

앞의 셋이 **MUST** 인 이유는 이것이 없으면 재개가 재개가 아니라 새 요청이기 때문입니다.

**해석 규칙**

- 재개 메시지는 **제시한 후보에 대해** 해석합니다. 새 질의로 읽지 않습니다.
- 답이 후보를 특정하지 못하면 다시 `TASK_STATE_INPUT_REQUIRED` 로 갈 수 있습니다. 다만 **직전과 같은 질문을 그대로 반복하지 않습니다** — 무엇이 부족한지 밝히거나 후보를 좁힙니다.
- 재개로 태스크가 종결되면 그 태스크의 후보 목록은 더 이상 유효하지 않습니다.

**어디에 두나**

| | |
| --- | --- |
| `Task.history` | 사용자 발화와 에이전트 질문. **밖에서 보이는 기록**이라 관찰자와 재시작한 오케스트레이터가 읽습니다 |
| 에이전트 내부 저장소 (`taskId` 로 색인) | 도구 결과·모델 메시지·후보 원본. 프로토콜에 안 나옵니다 |

`Task.history` 에 **질문과 답을 둘 다 남깁니다**(SHOULD). 남기지 않으면 태스크만 보고는 무슨 대화가 오갔는지 알 수 없고, 되묻기가 몇 번 돌았는지도 모릅니다.

내부 상태는 프로토콜의 관심이 아니지만 **태스크와 수명을 같이합니다** — 태스크가 정리되면(6.5절) 같이 버립니다. 안 그러면 샙니다.

## 6. 에이전트 안쪽의 설계 — 도구와 프롬프트

> 출처: **Anthropic, "Writing effective tools for agents"** 와 **Tool use with Claude**. 6.1절~6.4절은 그 지침을 옮긴 것이고 강도는 그 문서의 것입니다. 6.5절부터는 그 위에서 도메인 정책을 쓰는 법입니다.

A2A 는 에이전트를 **불투명한 것**으로 다루므로 안쪽을 정하지 않습니다(1.2절). 그래서 이 절의 근거는 A2A 가 아니라 위 지침입니다.

### 6.1 도구를 어떻게 고르는가

- **개수를 늘리지 말고 합칩니다.** `list_users`·`list_events`·`create_event` 를 따로 두지 말고 `schedule_event` 하나로 여러 조작을 처리합니다. `read_logs` 대신 관련 줄만 맥락과 함께 돌려주는 `search_logs` 를 둡니다.
- **작업 모양대로 만듭니다.** 도구는 *"사람이 하듯 에이전트가 과제를 쪼개고 풀 수 있게"* 해야 합니다. 여러 번 불러야 알 수 있는 것은 한 번에 주는 도구로 묶습니다.
- **기존 API 엔드포인트를 그대로 감싸지 않습니다.** *"도구가 많다고 결과가 좋아지지 않습니다."*

### 6.2 이름과 설명문

- **모호하지 않은 이름.** `user` 말고 `user_id`. *"새로 온 동료에게 이 도구를 어떻게 설명할지 생각하십시오."*
- **암묵적 맥락을 드러냅니다** — 특수한 질의 형식, 생소한 용어의 정의, 자원 사이의 관계.
- **네임스페이싱.** 서비스별(`asana_search`·`jira_search`)·자원별(`asana_projects_search`) 접두사로 가릅니다. 접두사와 접미사 중 무엇이 나은지는 **평가로 정합니다**(8장) — 효과가 작지 않습니다.
- *"설명문을 조금만 다듬어도 결과가 크게 달라집니다."*

### 6.3 무엇을 돌려주는가

- **신호를 줍니다.** 유연함보다 맥락상의 관련성이 먼저입니다. UUID·MIME 타입 같은 저수준 식별자를 빼고 `name`·`file_type` 같은 사람이 읽는 값을 줍니다.
- **자연어 식별자.** 임의의 영숫자 UUID 를 의미 있는 이름(또는 0부터 세는 번호)으로 바꾸면 **환각이 줄어 정확도가 눈에 띄게 오릅니다.**
- **응답 형식을 고르게 합니다.** `DETAILED`/`CONCISE` 같은 열거형을 두어 필요한 만큼만 받게 합니다 — 실측에서 간결 응답이 상세 응답의 **약 3분의 1 토큰**이었습니다(72 대 206).
- **기본값 있는 페이지·범위·필터·절단.** 절단할 때는 **지시를 함께 줍니다** — 넓게 한 번 검색하는 대신 좁게 여러 번 검색하도록 유도할 수 있습니다.
- XML·JSON·마크다운 중 무엇이 나은지 **정답은 없습니다.** 평가로 정합니다.

### 6.4 오류는 고칠 수 있게 냅니다

불투명한 오류 코드나 스택 트레이스 대신 **무엇을 어떻게 고치라는** 말을 줍니다 — 어떤 필터를 써야 하는지, 올바른 입력이 어떤 모양인지. 오류 응답으로 **더 토큰 효율적인 행동으로 유도**할 수도 있습니다.

이것은 4.3절(실패 규약)이 `status.message` 에 요구하는 것과 같은 원칙입니다.

### 6.5 프롬프트에는 도메인 정책만

프롬프트에는 **도메인 정책만** 담습니다. "친절하게 답하세요" 같은 문장은 토큰만 씁니다.

### 6.6 규칙 여덟 범주

전부 필요하지는 않습니다. **하나씩 짚어 보고 없어도 되는지 판단합니다.**

| # | 범주 | 무엇을 막나 | 예시 문장 |
| --- | --- | --- | --- |
| 1 | **책임 선언** | 정체성 흔들림 | "당신은 상품 재고·가격 조회와 주문 생성을 담당합니다." |
| 2 | **실행 강제** | 도구를 안 부르고 말로 때움 | "주문은 **반드시 도구를 실제로 호출해서** 만듭니다. 도구를 부르지 않고 '주문했습니다'라고 답하면 아무 일도 일어나지 않습니다." |
| 3 | **환각 차단** | 값을 지어냄 | "상품 코드를 손으로 만들어 넣지 마세요 — 검색 결과에서 받은 값만 씁니다." |
| 4 | **반복 금지** | 같은 호출 되풀이 | "같은 조회를 반복하지 않습니다. 이미 받은 결과를 다시 부르지 말고 그대로 씁니다." |
| 5 | **되묻기 정책** | 과도하거나 부족한 확인 | 7.2절 |
| 6 | **경계 선언** | 남의 일을 함 | "배송 추적 요청이 오면 이 에이전트의 일이 아니라고 답합니다." |
| 7 | **누설 금지** | 내부 구조 노출 | "도구 이름·필드 이름·내부 식별자는 답변에 노출하지 않습니다." |
| 8 | **단정 금지** | 확인 안 된 것을 확언 | "배송일을 단정하지 마세요. 재고 상태와 통상 소요일을 보여준 뒤 확정은 주문 후 안내된다고 밝힙니다." |

**3번이 가장 중요합니다.** 모델이 계산이나 조합으로 *만들어낼 수 있는* 값 — 코드, 식별자, 좌표, 금액 — 이 환각의 주 진입로입니다. "이 값은 도구로만 얻습니다"를 명시하지 않으면 모델이 그럴듯한 것을 지어냅니다. 그리고 그럴듯해서 사용자가 못 알아챕니다.

**모델이 약할수록 더 중요합니다.** 도구 호출에서 필수 인자가 발화에 없을 때, 상위 모델은 빠졌다는 것을 알아채고 되묻는 경향이 크지만 **하위 모델은 그럴듯한 값을 채워 넣습니다** — 사용자가 주지 않은 단위나 지역을 임의로 넣는 식입니다. 값싼 모델로 에이전트를 돌린다면 이 규칙 없이는 성립하지 않습니다.

가려면 세 가지를 함께 씁니다. **①** 프롬프트에 "지어내지 마십시오"를 명시하고, **②** 되묻기 정책(6.7절)으로 빠진 값을 물어보게 하고, **③** 도구 쪽에서 필수 인자를 검증해 빠졌으면 거절합니다. ③이 마지막 방어선입니다 — 프롬프트는 확률이고 검증은 확정입니다.

### 6.7 되묻기 판단 축

되묻기 정책은 **도메인마다 다릅니다.** 어떤 에이전트는 되묻지 않는 것이 맞고, 어떤 에이전트는 되묻는 것이 기본입니다.

흔한 기준인 *"되돌릴 수 있으면 실행"* 은 **틀렸습니다.** 조회도 되돌릴 수 있습니다 — 아무것도 안 바뀌니까. 그런데 틀린 조회 결과는 사용자가 믿습니다.

진짜 축은 이것입니다.

> **틀렸을 때 사용자가 알아채는가?**

| 상황 | 알아채나 | 판단 |
| --- | :-: | --- |
| 화면이 엉뚱한 곳으로 이동 | ✅ 보면 압니다 | 되묻지 말고 실행 |
| **엉뚱한 상품의 가격을 답함** | ❌ 그럴듯합니다 | **되묻습니다** |
| **엉뚱한 상품을 주문함** | ❌ 그리고 되돌리기 어렵습니다 | **되묻습니다** |
| 목록 정렬 순서를 임의로 정함 | ✅ 보면 압니다 | 실행 |

**조회 계열 에이전트에서 되묻기는 예외가 아니라 기본입니다.** 실측 사례에서 시나리오 30건 중 20건이 되묻기를 필요로 했고, 되묻기 루프가 안 닫혀 조회 계열 네 그룹의 통과율이 **0%** 였습니다.

되묻기를 쓴다면 2.5절의 마지막 규칙을 반드시 지킵니다 — **후보는 서로 구별되는 값을 가집니다.**

### 6.8 답변 형식 절을 따로 둡니다

프롬프트 끝에 `답변 형식:` 절을 둡니다. 공통으로 넣을 만한 것:

- 물은 것에 먼저 답하고, 조회 과정은 늘어놓지 않습니다
- 나열할 사실이 셋 이상이면 표로 정리합니다
- 내부 값(식별자·좌표·원시 코드)은 적지 않습니다
- 값이 없으면 없다고 적고, **조회하지 않은 것을 단정하지 않습니다**
- 실패하면 사유를 사용자 표현으로 설명합니다

### 6.9 프롬프트 전체 예시

```
당신은 상품 재고·가격 조회와 주문 생성을 담당합니다.

- 주문은 **반드시 도구를 실제로 호출해서** 만듭니다.
  도구를 부르지 않고 "주문했습니다"라고 답하면 아무 일도 일어나지 않습니다.
- **상품 코드를 손으로 만들어 넣지 마세요.** 검색 결과나 사용자 발화에서
  실제로 받은 값만 씁니다.
- 검색 결과가 여럿이면 임의로 고르지 말고 사용자에게 물어봅니다.
  틀린 상품의 가격을 답하면 사용자가 알아챌 방법이 없습니다.
- **같은 질문을 두 번 하지 마세요.** 직전에 물은 것과 같은 질문이 떠오르면,
  묻는 대신 가진 정보로 진행할 수 있는지 먼저 보세요.
- 같은 조회를 반복하지 않습니다. 이미 받은 결과를 그대로 씁니다.
- 사용자가 요청하지 않은 조회나 주문은 하지 않습니다.
- 배송 추적·반품·결제 수단 변경 요청이 오면 이 에이전트의 일이 아니라고 답합니다.
- **배송일을 단정하지 마세요.** 재고 상태와 통상 소요일을 보여준 뒤
  확정은 주문 후 안내된다고 밝힙니다.

답변 형식:

- 물은 것에 먼저 답하고, 조회 과정은 늘어놓지 않습니다.
- 나열할 사실이 셋 이상이면 표로 정리합니다.
- 도구 이름·필드 이름·내부 식별자는 노출하지 않습니다.
- 값이 없으면 없다고 적고, 조회하지 않은 것을 단정하지 않습니다.
- 실패하면 실패 사유를 사용자 표현으로 설명합니다.
```

## 7. 자가 점검 — 보증이 아니다

만든 것이 이 규격을 지키는지 확인합니다. **경로 A·B 모두 같은 검사를 받습니다.**

> **통과가 적합성 보증은 아니다.** 옮겨 적은 것만 봅니다 — 최종 근거는 `reference/a2a.proto` 다. 눈으로 못 잡는 것(직렬화·상태 전이·되묻기 루프)을 잡는 용도입니다.

### 7.1 자동 점검

배포물에 포함된 검사기를 돌립니다.

```bash
python conformance_check.py http://localhost:<포트>
```

검사 항목은 2장를 그대로 따릅니다. 통과하지 못한 항목은 어느 요건인지와 함께 출력됩니다.

**`--probe` 를 주면 왕복까지 봅니다.** 발화를 보내고, 되물어 오면 **후보를 골라 답을 보내 루프가 닫히는지** 확인합니다(2.5절). 이것이 형식 검사와 갈리는 지점입니다 — 재개 상태를 안 들고 있는 에이전트는 형식 검사를 전부 통과하고 여기서만 걸립니다. `returnImmediately` 를 뺀 블로킹 모드도 함께 봅니다(A2A 규격 3.5절).

모델을 실제로 부르므로 비용이 듭니다. 그래서 기본이 아니지만, **배포 전에는 반드시 한 번 돌립니다.**

### 7.2 수동 확인

**카드는 origin 에서 읽고, API 는 카드가 정한 주소로 보냅니다.** 둘이 다를 수 있습니다 — 경로 접두사(`https://host/agents/catalog`)나 프록시 주소가 붙기 때문입니다.

```bash
ORIGIN=http://localhost:<포트>          # well-known 은 여기 (2.4.1절)

# ① 카드가 나오나 — 안 나오면 설정 파싱이 실패한 것이다
curl -s $ORIGIN/.well-known/agent-card.json | jq .

# API 기준 URL 은 카드가 정한다. 이하 요청은 여기로 간다.
A=$(curl -s $ORIGIN/.well-known/agent-card.json \
    | jq -r '.supportedInterfaces[] | select(.protocolBinding=="HTTP+JSON") | .url' | head -1)
echo "API 기준: $A"

# ② 병렬 힌트가 실렸나 — 빠지면 병렬 실행이 조용히 죽는다 (4.1.1절)
curl -s $ORIGIN/.well-known/agent-card.json \
  | jq '.capabilities.extensions[] | select(.uri|test("tool-hints")) | .params'

# ③ 실제로 도나
TID=$(curl -s -X POST $A/message:send \
  -H 'Content-Type: application/a2a+json' \
  -d '{"message":{"messageId":"'$(uuidgen)'","role":"ROLE_USER",
       "parts":[{"text":"<이 에이전트가 받을 법한 발화>"}]},
       "configuration":{"returnImmediately":true}}' | jq -r .task.id)

# ④ 결과가 나오나
curl -s $A/tasks/$TID | jq '.status.state, [.artifacts[].name]'

# ⑤ 없는 태스크는 404 인가
curl -s -o /dev/null -w '%{http_code}\n' $A/tasks/nonexistent-id
```

### 7.3 배포 전 체크리스트

**카드**

- [ ] 필수 8필드가 모두 있습니다 (2.3절)
- [ ] `description` 에 **"…는 이 에이전트가 아니다"** 배제 문장이 있습니다
- [ ] 같은 오케스트레이터에 붙는 다른 에이전트와 `description` 이 겹치지 않습니다 — 나란히 놓고 읽어 봤습니다
- [ ] 확장 URI 의 도메인을 정했습니다 — `<도메인>` 을 그대로 두지 않았습니다 (4.1절)
- [ ] 모든 스킬에 `hints` 가 있습니다 (4.1.1절 — 없으면 병렬이 조용히 죽습니다)
- [ ] `capabilities` 에 선언한 기능을 실제로 구현했습니다
- [ ] `supportedInterfaces[0].url` 이 **밖에서 닿는 주소**다 (프록시 뒤면 `PUBLIC_URL`)
- [ ] 그 주소로 실제 요청이 갑니다 — 경로 접두사를 쓴다면 접두사 아래에 엔드포인트가 있습니다

**동작**

- [ ] `returnImmediately: true` 와 `false` 를 둘 다 지원합니다
- [ ] `A2A-Version` 헤더를 읽고, 모르는 버전이면 `VersionNotSupportedError` 를 냅니다 (2.2절)
- [ ] 없는 `taskId` 에 404 를 냅니다
- [ ] 종결 태스크에 메시지를 보내면 400 을 냅니다
- [ ] 되묻기가 왕복으로 닫힙니다 — 답하면 **같은 태스크가 이어집니다** *(검사기가 `--probe` 로 자동 확인)*
- [ ] 되묻기 후보가 서로 **구별되는 값**을 가집니다 (2.5절) *(자동)*
- [ ] 재개할 때 **원래 요청·직전 질문·후보 목록**을 들고 있습니다 (2.5절) *(자동)*
- [ ] 실패 시 `status.message` 에 **사람이 읽을 사유**가 있습니다 ("실패했습니다"가 아니라)

**모델·도구** (경로 A)

- [ ] 프롬프트에 환각 차단 규칙이 있습니다 — 모델이 지어낼 수 있는 값을 짚었습니다 (6.6절)
- [ ] 되묻기 정책이 있고 6.7절의 축으로 판단했습니다
- [ ] 모델에 보이는 도구를 필요한 것만 남겼습니다 (6.1절)
- [ ] 추론 강도를 명시적으로 설정했습니다 (5.8절)
- [ ] 화면 명령을 낸다면 도구 결과의 성공 여부를 보고 냅니다 (4.2절)

**운영**

- [ ] 포트가 다른 스택의 대역을 침범하지 않고, 배포 문서에 적었습니다
- [ ] 발화 5개로 실제로 돌려 봤습니다 — 성공·되묻기·실패·경계 밖 요청·긴 결과

### 7.4 안티패턴

| 하지 말 것 | 왜 |
| --- | --- |
| `hints` 를 빼먹습니다 | 병렬이 죽는데 **오류가 안 납니다.** 결과는 맞게 나와 테스트로도 안 잡힙니다 |
| `description` 에 "안 하는 것"을 안 씁니다 | 오케스트레이터가 엉뚱한 발화를 보냅니다 |
| 도구 전체를 allowlist 없이 노출합니다 | 목록이 길면 모델이 도구를 못 고릅니다 (5.5절) |
| 모델이 식별자를 만들게 둡니다 | 그럴듯한 값을 지어내고 사용자가 못 알아챕니다 |
| 되묻기 후보에 구별 불가능한 값을 줍니다 | 사용자가 골라도 같은 후보가 돌아옵니다 |
| 실패한 결과로 화면을 움직입니다 | 4.2절의 성공 판정을 빠뜨렸을 때 생깁니다 |
| 한 에이전트에 도메인 둘을 넣습니다 | `description` 이 배타적일 수 없게 됩니다. 나누십시오 |
| 조회 스킬과 변경 스킬을 한 에이전트에 섞습니다 | 조회까지 직렬로 떨어집니다 (4.1.1절). 나누는 편이 나을 수 있습니다 |
| 선언만 하고 구현 안 한 `capabilities` | 클라이언트가 시도하다 실패합니다. `false` 가 정직합니다 |
| 런타임 코드를 고칩니다 (경로 A) | 설계가 틀렸을 가능성이 높습니다. 먼저 물어보십시오 |

## 8. 평가 — 잘 도는지 어떻게 아는가

> 출처: **Anthropic, "Writing effective tools for agents"**. 이 절은 그 지침을 옮긴 것이고, 강도는 그 문서의 것입니다.

8장은 **프로토콜을 지키는지** 봅니다. 지켰는데도 답이 틀리거나 도구를 못 고를 수 있습니다. 그건 여기서 잡습니다.

### 8.1 과제를 현실에서 가져온다

- 평가 과제는 **실제 쓰임에서** 만들고, 실제 데이터·서비스를 씁니다.
- 좋은 과제는 **도구를 여러 번 — 때로는 수십 번 — 부르게** 합니다. 한 번 검색해 끝나는 과제는 아무것도 검증하지 못합니다.
- **단순한 샌드박스를 피합니다.** 복잡도가 없으면 도구가 시험되지 않습니다.

### 8.2 검증자를 붙인다

과제마다 **검증 가능한 응답이나 결과**를 짝지어 둡니다. 검증자는 정답과의 문자열 비교부터 모델에게 판정을 맡기는 것까지 범위가 넓습니다.

**형식·구두점·같은 뜻의 다른 표현 때문에 맞는 답을 틀렸다고 하는 검증자를 쓰지 않습니다.** 그런 검증자는 개선을 가로막습니다.

### 8.3 프로그램으로 돌린다

과제마다 **모델 호출과 도구 호출을 번갈아 도는 단순한 루프** 하나를 돌립니다.

평가 에이전트에게 도구를 부르기 전에 **추론과 피드백을 적게** 합니다 — 사고 사슬을 유도해 실효 지능이 올라갑니다.

### 8.4 정확도만 보지 않는다

| 지표 | 무엇을 말해 주나 |
| --- | --- |
| 정확도 | 답이 맞았는가 |
| 총 실행 시간 | 사용자가 기다리는 시간 |
| **총 도구 호출 수** | 같은 호출을 되풀이하면 도구 설명이나 인자가 잘못됐습니다 |
| **총 토큰 사용량** | 응답이 과하거나 카탈로그가 큽니다 |
| **도구 오류 수** | 많으면 설명이 불명확하다는 뜻입니다 |

**행간을 읽습니다.** 평가 에이전트가 정답을 아는 것이 아니다. 중복 호출은 인자를 손보라는 신호이고, 오류가 잦으면 설명을 손보라는 신호입니다.

### 8.5 전사를 모델에게 읽힌다

평가 실행의 전사를 이어 붙여 모델에게 줍니다. 전사 분석과 도구 설명 일괄 수정은 모델이 잘합니다.

### 8.6 held-out 을 나눈다

개선에 쓰는 과제와 판정에 쓰는 과제를 나눕니다. 안 나누면 과적합되고, 나누면 "전문가가 손으로 짠 구현" 을 넘는 개선까지 나옵니다.

## 9. 참조 자료

**여기 있는 것은 규범이 아니다.** 에이전트를 설계할 때 **"이런 것을 결정해야 합니다"는 목록**입니다. 각 항목의 제안은 출발점일 뿐이고, 도메인에 따라 다른 답이 맞을 수 있습니다.

### 9.1 실패 오인 — 도구는 성공했는데 모델이 실패라고 답한다

환각(없는 값을 있다고 함, 7.1절 3번)의 **반대 방향**입니다. 지금 6장은 한쪽만 막고 있습니다.

```
환각        없는 값을 있다고 한다         → 7.1절 3번이 막는다
실패 오인    있는 값을 없다·틀렸다고 한다   → 막는 장치가 없다
```

**실측 사례 둘.**

| 상황 | 도구 결과 | 모델의 답 |
| --- | --- | --- |
| 응답이 21,519자 | 성공, 값 정확 | **"조회에 실패했습니다"** |
| 결과 타입이 `Mapping` 이 아님 | 성공, 값 정확 | "이동했습니다" (화면은 안 움직임) |

**환각보다 조용합니다.** 도구 로그가 성공이라 어디를 봐도 정상으로 보이고, 사용자만 "안 됩니다"는 답을 받습니다. 그리고 다시 물어도 또 실패라고 합니다 — 사용자가 에이전트를 못 믿게 되는 경로입니다.

**제안 ① — 프롬프트에 짝을 넣습니다** (6.6절의 3번과 함께)

```
- 도구가 값을 돌려줬으면 그 값을 씁니다. 결과가 길거나 형식이 낯설다고
  실패로 단정하지 마세요.
- 결과에 명시적인 실패 표시가 있을 때만 실패로 봅니다.
  값이 안 보이면 "실패했다"가 아니라 "찾지 못했다"입니다.
- 잘렸다는 표시가 있으면 뒤에 값이 더 있을 수 있습니다. 없다고 단정하지 마세요.
```

**제안 ② — 태스크 상태는 모델의 말이 아니라 도구 결과로 정합니다**

모델이 "실패했습니다"고 답했다고 태스크를 `TASK_STATE_FAILED` 로 두면, 성공한 작업이 실패로 기록됩니다. 도구가 성공했으면 `COMPLETED` 이고, 모델이 결과를 못 읽은 것은 답변 품질 문제지 태스크 실패가 아니다.

**제안 ③ — 어긋남을 관측합니다**

도구 결과는 성공인데 답변이 실패를 말하면 그 자체가 신호입니다. 최소한 로그에 남깁니다. 이 조합에서는 화면 명령(`actions`)은 정상으로 나가고 답변만 실패라고 말해, 사용자가 가장 혼란스러워합니다.

**제안 ④ — 긴 결과를 자를 때 자른 사실을 밝힙니다** (5.6절 참고)

모델이 "값이 없습니다"와 "값이 잘렸습니다"를 구별할 수 있어야 없는 것을 단정하지 않습니다.

### 9.2 코드 레벨 테스트

8장은 **밖에서 두드리는 검사**다. 만드는 사람이 코드 레벨에서 무엇을 테스트해야 하는지는 다루지 않습니다.

**제안 — 모델과 도구 없이 프로토콜 층만 테스트합니다.** 매 테스트가 모델을 부르면 느리고 비싸서 아무도 안 돌리게 됩니다. 가짜 실행기를 주입해 프로토콜만 검사하면 초 단위로 끝납니다.

| 무엇을 | 왜 |
| --- | --- |
| 상태 전이 전수 — 합법·불법 | 전이 규칙(2.4절)이 한 군데에 모여 있어야 이게 가능합니다 |
| 종결 태스크 거절 4종 | 실수하기 쉽고 밖에서는 늦게 발견됩니다 |
| 직렬화 — camelCase, enum 문자열, 타임스탬프 | 눈으로 못 잡습니다 |
| 카드 생성 — 설정에서 카드로 | `hints` 누락 같은 조용한 결함을 잡습니다 |
| 되묻기 왕복 | 재개가 새 태스크를 만들지 않는지 |
| 아티팩트 조립 | 이름·`artifactId` 형식 |

**제안 — 규격 문서의 JSON 예시를 픽스처로 박습니다.** 필드명을 잘못 옮기면 여기서 깨집니다.

### 9.3 태스크가 `WORKING` 에서 영원히 멈추는 경우

모델 호출이나 도구 호출이 걸리면 태스크가 `COMPLETED` 도 `FAILED` 도 되지 않습니다. 클라이언트는 무한히 폴링합니다.

A2A 는 태스크 자체의 시한을 정하지 않습니다. **제안** — 태스크에 시한을 두고, 넘으면 `FAILED` 로 종결하며 `status.message` 에 시한 초과임을 밝힙니다. 시한 값은 도메인이 정합니다.

### 9.4 중복 메시지

클라이언트가 타임아웃으로 재전송하면 **태스크가 두 개 생깁니다.** 쓰기 에이전트에서는 그대로 중복 실행입니다.

A2A 규격 3.3.1절이 길을 열어 뒀습니다.

> **Send Message** operations MAY be idempotent. Agents may utilize the `messageId` to detect duplicate messages.

**제안** — 최근 `messageId` 를 기억해 같은 것이 오면 새 태스크를 만들지 않고 기존 태스크를 돌려줍니다. 기억하는 창(개수·시간)은 도메인이 정합니다. 조회만 하는 에이전트라면 안 해도 손해가 작습니다.

### 9.5 의존 서비스가 죽었을 때

도구가 죽으면 스킬을 수행할 수 없는데 카드는 그대로 광고합니다. 오케스트레이터는 계속 보내고, 매번 실패합니다.

**제안 셋 — 어느 것이 맞는지는 도메인에 달렸습니다.**

| 안 | 장점 | 단점 |
| --- | --- | --- |
| 그대로 두고 `FAILED` 로 답합니다 | 단순합니다 | 오케스트레이터가 계속 보냅니다 |
| 해당 스킬을 카드에서 뺍니다 | 라우팅이 피해 갑니다 | 카드가 자주 바뀝니다. 캐시와 어긋납니다 |
| `TASK_STATE_REJECTED` 로 답합니다 | "지금은 못 합니다"가 분명합니다 | 클라이언트가 이 상태를 다룰 줄 알아야 합니다 |

**별도 제안 — 헬스 체크.** 카드가 200 을 내는 것은 "떴다"는 뜻이지 "일할 수 있습니다"는 뜻이 아니다. 모델이나 도구가 죽어도 카드는 나옵니다. 둘을 구별할 방법이 필요하면 별도 엔드포인트를 둡니다.

### 9.6 재시작 시 진행 중이던 태스크

6.5절는 메모리에 둬도 적합하고 `TaskNotFoundError` 404 를 내면 된다고 적었습니다. **클라이언트가 그것을 어떻게 다뤄야 하는지는 정하지 않았습니다.**

**제안** — 클라이언트는 폴링 중 404 를 "실패"가 아니라 **"결과를 알 수 없음"** 으로 다룹니다. 작업이 실제로 수행됐을 수도, 안 됐을 수도 있습니다. 쓰기 작업이라면 재시도가 위험하므로, 실패로 단정해 자동 재시도하면 안 됩니다.

### 9.7 관측 가능성

이 문서는 로그에 무엇을 남길지 정하지 않습니다.

**제안** — 모든 로그에 `taskId` 와 `contextId` 를 넣습니다. 없으면 오케스트레이터의 한 요청이 에이전트의 어느 태스크가 됐는지 추적할 수 없고, 문제가 생겼을 때 로그를 맞춰 볼 방법이 없습니다.

### 9.8 값이 정해지지 않은 것들

이 문서가 값을 적어 둔 곳 중 **근거가 판단뿐인 것.**

| 값 | 지금 | 정하는 법 |
| --- | --- | --- |
| 도구 재시도 횟수 (4.3절) | 권장 2 | 재시도 1회로 풀리는 비율을 재면 근거가 생깁니다 |
| **확장 URI 의 도메인** (4.1절) | `<도메인>` — **반드시 정해야 합니다** | 붙을 플랫폼이 공표한 값을 쓰거나, 자기 프로파일이면 소유 도메인으로 |
| 아티팩트 **이름** (4.2절) | `answer`/`actions`/`candidates`/`resolve`/`errors` | 오케스트레이터와 합의해야 합니다. `candidates`·`errors` 는 필드 표가 있고, `actions` 는 화면이 정합니다 |
| `artifactId` 형식 (4.2절) | `{taskId}:{name}` | 유일하기만 하면 규격은 만족합니다 |
| 태스크 보존 시간 | 예: 1시간 | 폴링 주기와 재시작 빈도에 달렸습니다 |

## 10. 부록

### 10.1 용어 — 찾아보기

핵심 넷(Task·Context·Message·Artifact)은 1.3절 에서 그림과 함께 설명합니다. 여기는 빠르게 찾아보는 표입니다.

| 용어 | 뜻 |
| --- | --- |
| **에이전트** | 1.1절 |
| **오케스트레이터** | 에이전트를 부르는 쪽. 그 자신도 에이전트일 수 있습니다 |
| **Task** | 작업 단위. `taskId` 를 갖고 상태 기계를 따릅니다 |
| **Context** | 여러 Task 를 묶는 대화 단위. `contextId` |
| **Artifact** | Task 의 산출물. 이름과 `Part` 목록을 갖습니다 |
| **Part** | 내용 조각. text / raw / url / data 중 하나 |
| **Skill** | 라우팅용 설명문. 호출 시그니처가 아니다 |
| **되묻기** | 정보가 부족할 때 사용자에게 묻는 것. `TASK_STATE_INPUT_REQUIRED` |
| **종결 / 중단** | 종결은 되돌아올 수 없고, 중단은 재개할 수 있습니다 |
| **적합** | 2장를 만족함 |

### 10.3 이 규격이 A2A 위에 더한 것

A2A 만 아는 클라이언트도 우리 에이전트를 쓸 수 있습니다. 아래는 **더 잘 쓰기 위한** 약속입니다.

| 더한 것 | 왜 | 어디 |
| --- | --- | --- |
| 아티팩트 이름 규약 | A2A 는 그릇만 정하고 내용은 안 정합니다 | 4.2절 |
| `artifactId` 형식 | 폴링 클라이언트의 대조 편의 | 4.2절 |
| `tool-hints` 확장 | `AgentSkill` 에 부작용을 밝힐 자리가 없습니다 | 4.1.1절 |
| `progress` · `usage` 확장 | A2A 에 없는 개념 | 4.1.2절 |
| 실패 규약 | `TASK_STATE_FAILED` 의 내용을 A2A 가 안 정합니다 | 4.3절 |
| `errors` 아티팩트 | A2A 에 부분 실패를 표현할 자리가 없습니다 | 4.3절 |
| 되묻기 후보 구별 요건 | A2A 는 `INPUT_REQUIRED` 만 정하고 후보 형식은 안 정합니다 | 2.5절 |
